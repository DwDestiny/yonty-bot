# 发版和 Release 说明的写法

> 1.0.0 · 2026-11-25 · 维护：Yonty Bot contributors

发版的人读这一页：版本号怎么升、更新日志写在哪、GitHub Release 的标题和正文怎么写、发之前查什么。

## 1. 版本号和标签

- 版本号只写在根目录 `VERSION`，别处都是抄它。
- 新功能或改了行为：升次版本（3.15.1 → 3.16.0）。只修缺陷、不改行为：升修订号（3.15.0 → 3.15.1）。
- 组织、状态格式这类不兼容的大改：升主版本，并写清升级步骤。
- 标签叫 `v<版本>`，打在合进 main 的那个提交上（不是分支上的）。标签一律带 `v`，已有的标签不改名、不移动。
- 纯文档改动不升 `VERSION`，也不发版。
- 升级要求写在根目录 `UPGRADE.json`：`wait_below` 是“低于哪版升上来要等在跑的任务结束”，`notes` 是“要人手工做的事”。有人工步骤的版本，三处都要写：`UPGRADE.json` 的 `notes`、`CHANGELOG.md` 该版标题、Release 正文的“升级要做什么”。

## 2. 三处记录各写什么

| 地方 | 给谁看 | 写什么 | 篇幅 |
| --- | --- | --- | --- |
| `CHANGELOG.md` | 想知道“这版有什么变化”的使用者 | 每版按 新增、变更、修复、移除、安全 分组，用使用者看得懂的话；有人工步骤的标出来 | 一版几行到十几行 |
| `docs/guide.md` 的“变更记录” | 维护者、帮人装机的智能体 | 实现细节：配置键、状态文件、命令参数、回滚办法、踩过的坑 | 不限，允许长 |
| GitHub Release | 在仓库首页点进来的人 | 从 `CHANGELOG.md` 当版那一节改写：这版给你什么、升级要做什么、已知问题 | 一屏 |

分工规则：

- 先写 `docs/guide.md` 的变更记录（细），再从它提炼 `CHANGELOG.md`（粗），最后从 `CHANGELOG.md` 改出 Release 正文（更短）。同一件事三处说法可以不同，事实必须一致。
- `CHANGELOG.md` 里出现的版本号、日期，以标签为准。日期取标签所在提交的北京时间日期，Release 页显示 UTC，两者可能差一天，以 `CHANGELOG.md` 为准。
- 一个事实只在一处写全。`CHANGELOG.md` 不抄 `docs/guide.md` 的实现细节，需要时链接到它。
- 没打标签的版本，在 `CHANGELOG.md` 里写明“没有单独的标签和 Release，随 `v<下一个有标签的版本>` 发布”。
- 查不到日期就写“日期未查到”，不猜。

## 3. Release 标题

格式：`v<版本> · <一句话>`，一句话不超过 15 个字，写这版最值得说的一件事，不写“更新”“修复若干问题”。

| 版本 | 好的标题 |
| --- | --- |
| 3.15.1 | `v3.15.1 · 飞书子任务补齐字段` |
| 3.14.0 | `v3.14.0 · 任务闭环` |
| 3.2.0 | `v3.2.0 · 自动更新和决策点` |

不要用：不带 `v` 的（`3.15.1 …`）、带产品名前缀的（`Yonty Bot 1.2.1`）、只有版本号的（`v3.13.0`）。已发的 Release 标题不回改。

## 4. Release 正文模板

正文用中文，一屏内。三节固定，没有内容的节写“无”，不删节。

```markdown
## 这版给你什么
- 用使用者的话写 2～5 条，每条一句：变了什么、对你有什么影响。
- 修复类放在最后，写“修复：……”。

## 升级要做什么
- 一般版本写：`/upgrade` 直接升，不用做别的。
- 升级会等任务跑完的版本写：升级会等在跑的任务结束。
- 有人工步骤的版本，编号写出每一步和命令。

## 已知问题
- 已经知道、这版没修的问题，一条一行。没有就写“无”。

完整记录：[CHANGELOG.md](https://github.com/<所有者>/<仓库>/blob/main/CHANGELOG.md)
```

写法要求：

- 内部名词换成看得懂的话：不写 `tasks.update`、`TRANSITIONS`、提交号、内部函数名；配置键、命令这类用户会碰到的，用代码格式原样写。
- 一条只写一件事。不写“若干”“优化了一些”。
- 不放实例数据：真实的用户名、群和用户 ID、应用凭证、服务器地址、私人路径。发版前通读一遍，找到敏感信息只报位置，不抄进任何地方。
- 不写人名、公司名。

## 5. 发版前检查

按顺序，一项不过不发。

1. `VERSION` 已改成新版本号，且满足格式 `主.次.修`。
2. 两份 README 开头的版本行（`README.md`、`README.en.md`）已同步。
3. `docs/guide.md` 的“变更记录”已加这一版。
4. `CHANGELOG.md` 已加这一版，日期是今天（北京时间），分组不空着。
5. 有人工步骤、或需要等任务跑完：`UPGRADE.json` 已改，与 `CHANGELOG.md` 的标注一致。
6. 改了 `app/rules/` 或启动参数：重跑 `--cache-check`。
7. 全量测试通过：`python3 -m unittest discover tests`。仓库有 CI 时，以 CI 全绿为准。
8. 合并到 main 后，工作区干净，`git log -1` 是要打标签的那个提交。
9. 通读 Release 正文，确认没有实例数据和敏感信息。

## 6. 发布步骤

```bash
git tag v3.15.1 <提交号>
git push origin v3.15.1
gh release create v3.15.1 --title "v3.15.1 · 飞书子任务补齐字段" --notes-file release-notes.md
```

- `release-notes.md` 是临时文件，发完删掉，不进 Git。
- 先建草稿也行：加 `--draft`，检查渲染后再 `gh release edit v3.15.1 --draft=false`。没发布的草稿可以直接删。
- 发出去的 Release 不回改标题和正文。写错了在下一版的说明里更正，并在 `CHANGELOG.md` 里写明。
- 标签打好推上去就不要重打：重打会让已经下载的人和 `CHANGELOG.md` 对不上。新标签用轻量标签（`git tag v<版本> <提交号>`）；只有 `v1.0.0` 是带说明的标签。

## 7. 示例

下面是 3.15.1 的 Release，按本页模板写。

标题：`v3.15.1 · 飞书子任务补齐字段`

正文：

```markdown
## 这版给你什么
- 方案里的子任务也写上开始时间、截止时间、说明和自定义字段，并放进项目的分组。
- 以前建的子任务也会补齐，不用手工改。
- 修复：进行中写过一次字段、之后被自动勾掉的任务，补上结束时间。

## 升级要做什么
`/upgrade` 直接升，不用做别的。

## 已知问题
无

完整记录：[CHANGELOG.md](https://github.com/<所有者>/<仓库>/blob/main/CHANGELOG.md)
```

## 8. 已有 Release 的现状

- 1.0.0 到 3.15.1 共 30 个标签、30 条 Release，没有草稿和预发布。1.1.0、2.0.0、2.0.1 没有标签，并入下一个有标签的版本。
- 3.2.0 以前的正文有人写了详细说明，3.3.0、3.4.0 只有一句“见 guide”，3.13.0、3.12.0 等只有几个字或没有正文，标题格式也不统一。这些已发的不回改；`CHANGELOG.md` 补齐了每一版的说明。
- 从本页起，新发的 Release 照上面的标题和模板写。
