# 架构与路线

> 1.0.0 · 2026-11-22 · 维护：Yonty Bot contributors

本文回答四件事：代码分几层、每层管什么；团队怎么组织（一件事一个负责人）；智能体之间怎么汇报、怎么盯进度；提示词、钩子和决策怎么按路由拆。每条都标明是实测、是从文档看来但没有验证，还是判断。

## 1. 分层

| 层 | 管什么 | 现在的代码在哪 |
|---|---|---|
| 1 运行时适配 | 把各家 CLI 的输出统一成一组事件：开始、文字、工具、用量、额度、结果。每个适配器声明能力开关：能否分叉、能否压缩、能否设花费上限、费用单位（美元或 token） | `tasks.claude_args`、`tasks.session_cmd`、`run` 里解析 stream-json 的部分 |
| 2 调度与优化 | 会话存储、缓存策略（固定前缀、预热、热缓存分叉、过期前压缩）、检查点、额度提醒、卡死检测、验证闸门、云端执行 | `bridge` 的会话表和 `compact_*`；`tasks` 的预算、额度、验证、云端 |
| 3 团队 | 事和负责人、档案、帮手、任务状态机、智能体之间的消息 | `tasks` 的角色、`sibling_*`、`record_text`、事件和收件箱 |
| 4 渠道与身份 | 收发消息；认定身份；按路由给这条消息配提示词、钩子、工具 | `bridge` 的飞书、企微、旁听、任务命令 |
| 决策层（横跨各层） | 收拢所有判断点，默认行为不变，可换成用户自己的决策模型 | 现在散在守则和代码里 |

上层只看能力开关，不看底下是哪家 CLI。身份在第 4 层认定一次，下面各层只看路由。

## 2. 团队：一件事，一个负责人

### 2.1 概念

- **事**：项目里一块需要长期有人管的东西。可以是长期的（一个模块、一条业务线），也可以有终点（一次迁移）。一个大项目里有很多件事；新项目只有一件“主线”。
- **负责人**：等于“这件事 + 它的档案”。会话只是负责人现在用的身体：缓存还热就接着上次的会话，凉了就换一个新会话、读档案接着干。对外始终是同一个负责人。
- **协调人**：每个聊天一个会话，跟人沟通、判断活属于哪件事、派活、收回报、对人汇报。它不写代码。
- **帮手**：要“新鲜眼睛”时派的评审这类会话，每次新开，只看改动、只出意见，意见写进档案。帮手不写代码，不顶替负责人。

### 2.2 为什么这样设计（来源和实测）

| 依据 | 来源 | 结论 |
|---|---|---|
| 状态放文件、新开上下文读文件，比单靠压缩可靠 | Anthropic《Effective harnesses for long-running agents》：进度文件 + git + 功能清单，每个新会话先读它们；文中说单靠压缩不够 | 负责人绑在档案上，不绑在会话上 |
| 缓存 1 小时过期，本项目的聊天间隔大多超过 1 小时 | 本项目实测（3.2 的缓存账） | 续接一个凉掉的大会话要整段重写缓存，不如新开读档案 |
| 多个写手并行改耦合的东西会冲突；可行的是“写只有一个线程，其他智能体只出意见” | Cognition《Don't Build Multi-Agents》和 2026 年的续篇 | 同一件事同时只跑一个任务；跨事改动交给一个负责人一次改完；评审只读 |
| 按上下文拆，不按角色拆；“产品→需求→开发→测试”接力是传话游戏 | Anthropic《Building multi-agent systems》《Building agents: When to fold subagents into your main agent loop》 | 方案、实现、测试、返工都归同一件事，不再按角色接力 |
| 测试要独立于写代码的人；接力写代码不划算 | AgentCoder（2023，作者自测，GPT-3.5）：只写代码 61.0%，加独立测试 64.0%，再加跑测试反馈 79.9%，提升主要来自两者一起用；MAST（2025，1642 条轨迹）：多智能体失败里验证缺失或出错约占四分之一，交接丢信息单项都不到 3%；MetaGPT、ChatDev、BMAD 没找到同底座的独立对照 | 加“验收”：开工前只看任务书写测试，负责人不能改；角色只出意见或独立产物，不接力写同一块代码 |
| 持久身份、一次性会话 | Gas Town（Steve Yegge）：“persistent identity but ephemeral sessions”；Beads 用 `bd prime` 给新会话注入项目记忆 | 和本设计同一思路，已有人做成产品 |
| 同一件事不管从哪个聊天派来都该是同一个负责人；分开的是权限，不是负责人 | 主人 2026-11-22 定；取代 3.2.1 按聊天分负责人的做法 | 负责人的键只有“项目 × 事”，谁派的活都接着同一个会话。什么话能对谁说，由各聊天的主控按 IM 层识别的身份把关；身份只另外决定档案里决定和约定的分量，见 2.4 |

### 2.3 怎么划分

- 新项目先只有主线。某块活总是单独派、边界清楚时，起一件新的事：派活时写 `事情: 名字`，没有就自动建。
- 拆分、合并已有的事，先问主人。
- 协调人判断活属于哪件事，写进 `[派活]`。它在每份任务回报里看到项目现有的事；派活后服务告诉人“归到哪件事”，新开的事会列出已有的，归错了好改。服务只把相近的名字（一个包含另一个）归到已有的事，不靠路径或关键词猜。
- 判断，未验证：按 git 历史里“总是一起改的文件”自动建议怎么分。先在一个几百次提交的真实仓库上试一次，事先定好及格线，不过就不做。
- 一件事大到压缩后还装不下时，再考虑拆。阈值要实测。

### 2.4 怎么记

| 记什么 | 存在哪 | 谁写 | 谁读 |
|---|---|---|---|
| 档案：目标、现状、待办、已定的决定、别处留言 | `state/team/<项目>/<事>.json` | 只有服务写，按负责人交回的 `[交接]` 分栏合并 | 这件事的新会话 |
| 笔记：坑、入口、零碎经验 | 同名 `.md`，只追加 | 服务 | 同上，只带最后一段 |
| 项目约定：所有事都遵守的做法 | `_约定.md` | 服务，来自主人派的任务的 `约定：` | 同项目的所有事 |
| 事件流：派活、进展、提问、完成 | 任务目录的 `events.jsonl` | 服务 | 协调人、`/任务`、`/团队` |

- 分栏：`现状`、`待办` 整栏替换；`决定` 追加、去重，写为什么；`约定` 进项目级；`通知 某事：` 进那件事的别处留言，只给已有的事，否则留在笔记里。
- 档案太长时按重要程度截：目标、现状、待办、决定在前，先丢笔记。
- 云端任务开工时同样带上档案；云端的交接写在提交正文里，不进档案。
- 权限按派活人身份分（身份由 IM 层识别，消息里自称不算）：

  | | 主人派的任务 | 同事派的任务（主人批过才开工） |
  |---|---|---|
  | 接着负责人的会话、成为会话头 | 能 | 能（主人 2026-11-22 定：不为隔离多花 token，话由主控把关） |
  | 写现状、待办、笔记、通知 | 能 | 能 |
  | 写已定的决定 | 能 | 能，标上“某同事派的、主人没确认”，后来的负责人可以改 |
  | 写项目约定 | 能 | 不能，记进笔记等确认 |
  | 派活回复里列项目现有的事 | 只在主人私聊里列 | 不列：事的名字可能是主人私下起的 |

- 档案给这件事以后所有任务看，交接时只写工作上的事实，不写谁在哪个聊天里说了什么。
- 主控把关有一个缺口：`[进展]` 直接发到聊天；主控没跑成或回 `[不回]` 时，完成和失败的原话也直接发。所以任务提示里写明“进展、提问、总结只说这次任务本身，不提从别处听来的事”。这是提示，不是硬拦。
- 同事发给任务的 `短名#N 内容` 先交给主控，主控写 `[任务指令]` 才转进任务；主人的直接转。同事的任务也会成为会话头，主人下一个任务分叉时上下文里带着这些经主控转过的话，每条都标着是谁说的。
- 同一件事同时只跑一个任务，不分派活人：同事的任务停在提问时，主人的新活也排在后面。

### 2.5 和 3.x 的差别

| 3.x | 现在 |
|---|---|
| 兄弟会话按“项目 × 角色 × 受众”分 | 负责人按“项目 × 事”分，不分聊天；派活人身份管权限；角色只决定模型和工具 |
| 交接笔记只追加，一份流水账 | 档案分栏：现状和待办替换，决定追加，另有项目约定和别处留言 |
| 同项目同角色的任务可以同时分叉出几个 | 同一件事同时只跑一个（在跑或停在提问都算），后来的排队；停在提问、失败的会话不拿来分叉 |
| 换模型的活挤掉会话头 | 会话头按模型分，换模型的活不挤掉原来的 |
| 评审做完也会变成会话头 | 帮手只写档案，不顶替负责人 |
| 大活按产品 → 需求 → 开发 → 评审接力 | 一件事一个负责人做到底，评审只出意见 |

### 2.6 还没验证的

- **档案够不够用**：这决定整个设计。验法：拿一件真实的事，只给新会话档案和一个后续任务，看它会不会推翻或重做以前的决定，再和续接一个凉掉的会话比花费。这是路线第 3 步的完成标准。
- 土豆姐（Lauren Tan）的演讲和 pstack 是这套思路的另一来源：先让智能体能自己验证，纠正一次就沉到更硬的一层（代码、lint、规则），一件事一个新上下文。两篇中文文章没读到。

## 3. 智能体之间的消息

统一成一种信封，现有通道都改成用它：

| 字段 | 说明 |
|---|---|
| `from` / `to` | 人、协调人、负责人、帮手。负责人之间不直接对话，跨事的话写进对方的档案；负责人和协调人之间经过存储 |
| `kind` | 往上：进展、提问、检查点、完成、失败、交接；往下：指令、回答、加预算、取消 |
| `task` / `body` / `ts` | 任务号、内容、时间 |
| `needs_reply` | 往上的提问要不要等回复；等回复时任务进入“等回复”，不占运行名额 |

- 往上：现在的 `events.jsonl`。往下：`inbox.jsonl`，任务在跑时由 `PostToolUse` 钩子在下一次工具调用后塞进去。
- 盯进度一律读存储，不去问智能体本身，问一次就是一轮 token。

## 4. 路由：按身份和场景拆上下文

实测（2026-11-21，haiku，同一句输入，单次调用的固定开头）：

| 启动参数 | 固定开头（token） |
|---|---|
| 现在的参数 | 46219 |
| 加 `--disable-slash-commands` | 39261 |
| 加 `--setting-sources project,local` | 30840 |
| 只给 Bash、Read、Grep、Glob | 24619 |
| 三项都做 | 19644 |

| 路由 | 提示词片段 | 钩子 | 工具和记忆 |
|---|---|---|---|
| 主人私聊 | 人设、风格、派活、改守则 | 身份、私密路径 | 全部工具、技能、主人的全局设置和记忆 |
| 群里被 @（同事） | 人设、风格、群聊礼仪、派活 | 身份、私密路径、git | 不带主人的全局设置和记忆，技能只留读 IM 的 |
| 旁听 | 只有插话规则 | 只读 | 先交给决策层判断要不要插话 |
| 任务回报（协调人） | 收尾规则、花费说明 | 同来源路由 | 同来源路由 |
| 事的负责人和帮手 | 档案、角色配方、交接格式 | git、任务收件箱 | 按配方给工具，不带聊天规则 |

- 每多一种开头就多一份缓存，所以路由要少。
- 钩子不花 token，拆钩子是为了安全。
- 现在同事在群里 @ 机器人时，会话里也带着主人的全局规则和偏好。拆路由后这个问题顺带解决。

## 5. 决策点

| 决策点 | 现在谁决定 | 适合交给决策模型 |
|---|---|---|
| 旁听时要不要插话 | 每批开一个 Claude 会话 | 是，优先 |
| 聊天里回还是派成任务 | 协调人 | 是 |
| 活属于哪件事、派什么帮手、用什么模型和思考档 | 协调人 | 是 |
| 本机还是云端 | 协调人，条件不满足自动改回本机 | 是 |
| 预算估多少；到检查点后继续还是停 | 协调人，没写用同类历史 × 1.5 | 是 |
| 任务回报：自己收尾、问人、不回 | 协调人 | 要读完整回报，便宜模型未必够 |
| 分叉还是新开、何时压缩、何时换会话、卡死判定、额度提醒 | 规则 | 能接，规则已够用 |
| 拆分、合并事 | 主人 | 否，先问人 |
| 身份、审批、权限、钩子拦截 | 规则 | 永远不交给模型 |

- 接口统一：输入是这个决策点需要的事实，输出是固定格式的 JSON，超时或出错退回默认。
- 决策模型走用户自己填的 OpenAI 兼容接口，不经过本项目的服务器。
- 从第一天起记决策日志。接决策模型时先跑影子模式：同时判断、只记不用，对比后按决策点逐个切换。

## 6. 任务状态机

允许的转换写在 `app/tasks.py` 的 `TRANSITIONS` 表里，所有改状态都经过 `tasks.update` 校验，不在表里的转换直接报错。测试按表逐条检查。

## 7. 运行时：Claude Code 和 Codex

| 能力 | Claude Code（已实测） | Codex（来自文档，未验证） |
|---|---|---|
| 无头运行、流式事件 | `claude -p --output-format stream-json` | `codex exec --json`，或 app-server JSON-RPC |
| 续接 | `--resume <id>` | `codex exec resume <id>` |
| 分叉 | `--fork-session`，带父会话的累计花费 | `codex fork`（交互式），无头形式没找到 |
| 压缩 | 无头 `/compact`，`--autocompact` | 有自动压缩，无头手动压缩未知 |
| 花费上限 | `--max-budget-usd` | 没有，要按 token 自己截 |
| 钩子 | settings 里的 PreToolUse 等 | `hooks.json` 或 `config.toml` 的 `[hooks]` |
| 额度 | stream-json 的 `rate_limit_event` | app-server 的 `account/rateLimits/read` |

费用单位按运行时走：Claude 用美元当量，Codex 用 token。检查点改成“占订阅额度的百分比”，两边可以统一。这是判断，要等 Codex 适配器实测。

## 8. 路线

| 步 | 做什么 | 怎么算完成 |
|---|---|---|
| 0 | 新仓库、目录方案、状态转换表、事和档案 | 现有测试全过；状态转换、档案合并、同事排队有测试 |
| 1 | 按层拆成包 | 行为不变，测试全过，作者的实例切到本仓库 |
| 2 | 按路由拆上下文 | 每种路由量出固定开头和缓存命中率 |
| 3 | 档案验证、统一消息、决策层 | 档案验证通过（见 2.6）；决策日志有数据 |
| 4 | Codex 适配器 | 本机装好、能力开关实测，一个真实任务跑完 |
| 5 | Yonty 子应用 | 先确认 Yonty 扩展的形态（本机这版还不支持扩展命令） |
