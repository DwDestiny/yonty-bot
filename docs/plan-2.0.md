# 2.0 升级方案：三层智能体和定时任务

> 方案（已评审一轮）· 2026-11-22 · 维护：Yonty Bot contributors

本文是下一个大版本（2.0）的方案，只定做什么、为什么、怎么验收，不含实现代码。现有代码和文档以 1.3.0 为准。每条结论标“已核实”（附来源，见第 15 节）或“判断”。

## 0. 先说结论

1. **三层**：主控（每个聊天一个，只沟通、分流、放行、汇总）→ 项目经理（每个项目至少一个，管这个项目的需求分派、先后、收尾）→ 执行层（事负责人、帮手、定时任务的每次运行）。项目经理在事负责人之上，把一整件事交给一个负责人，自己不写代码，不是接力里的一环。所以 `docs/tasks.md` §6.1.1、§6.2 的“一件事一个负责人、不按角色接力”全部保留。
2. **主控不被卡住**靠四样东西，不靠提示词：要来回几十步的设备操作只能在任务里做（设备租约，见 4.8）；聊天这一轮跑着时新消息会塞进这一轮（4.2）；不带编号的回复按固定顺序路由到正在等它的那个任务（4.5）；任务回报交给项目经理，不再进主控的上下文（4.3）。
3. **并发不用 `max_running` 这个死数**。服务把机器余量、在跑任务的实际占用、待开任务的预估占用和订阅额度交给派活的智能体，由它定放不放行；服务只守一条内存底线和一个防失控的总数上限（第 5 节）。
4. **定时任务**支持 cron、固定间隔、一次性，以及“这次跑完由智能体定下次”。智能体每次交回下次时间和理由，服务按上下限钳住。放慢、收窄、停掉可以自己定，事后上报。加快、扩大到创建时的上下限之外，只能提议。高频的先跑不花 token 的探针，过线才叫醒智能体（第 6 节）。
5. **汇报链只有一条**：执行层 → 项目经理 → 主控 → 主人。定时任务也走这条链。级别由发送方定、写理由。服务自己发现的“没跑起来”“连续失败”有最低级别，智能体压不下去。服务本身挂了，由一个独立的定时器发现并直接私聊主人（第 7 节）。
6. **设计原则**（主人 2026-11-22 定）：能交给智能体判断的，服务只给信号，由智能体定并留理由。只有安全、授权和防失控的部分留作硬护栏，每条护栏写明为什么不能交给智能体。第 11 节把方案里每个常数都过了一遍。
7. 有 6 件事等主人定，都有默认建议，不卡方案（第 13 节）。最大的一件是主人日常电脑能不能放给任务用。

## 1. 术语

| 术语 | 意思 |
|---|---|
| 主人 | 机器人的主人，实例配置里的 `owner_*` |
| 主控 | 第一层。每个聊天一个会话，就是现在的“协调人” |
| 项目经理 | 第二层。一个项目至少一个，身份是“项目 + 项目档案”，会话可以换 |
| 事负责人 | 第三层。现有概念：“项目 × 事 + 档案”（`docs/architecture.md` §2） |
| 帮手 | 第三层。评审、验收，每次新开，只出意见或独立产物 |
| 定时任务 | 按时间表反复或一次性叫醒智能体的对象，编号 `短名#S<N>` |
| 运行 | 定时任务的一次执行。它是一个普通任务，编号 `短名#N`，现有任务命令都能用 |
| 探针 | 服务按频率跑的脚本，不花 token，决定要不要叫醒智能体 |
| 动作 | 服务替智能体执行的窄脚本，参数先校验，凭据只有服务能读 |
| 设备 | 机器人能远程操作的电脑，例如主人的日常电脑、测试电脑。实例配置项 `devices` |
| 设备租约 | 一台设备同一时间只给一个任务用的占用记录 |
| 待人回复 | 某个智能体在等人回话或等人做一个动作，服务登记的一条记录 |
| 信号 | 服务算好、交给智能体做判断的事实，例如可用内存、连续几天没异常 |
| 护栏 | 服务硬执行、智能体改不了的限制 |
| 决策日志 | 智能体每个决定的输入、选择和理由，`state/decisions.jsonl` |
| 看板 | 每个项目一行的现状，项目经理写，主控读 |

## 2. 需求拆解：原话里的真问题

主人的原话见任务书，下表把它拆成要解决的问题。主人多数时候在私聊里跟主控说话，同时推进几个项目。

| 编号 | 问题 | 来自 | 现在为什么不行 |
|---|---|---|---|
| R1 | 主控不能被一件长活占住 | 三层原话；场景 1 | 聊天消息按会话排一个队（`bridge.enqueue`），主控一轮在做几十步设备操作时，主人的新消息只能排在后面 |
| R2 | 每个项目有自己的负责人，方案、新需求、问题都交给它，它再往下派 | 三层原话 | 现在“项目”只是任务编号的前缀，没有项目级的智能体。派活、收尾都由聊天里的主控做 |
| R3 | 多个项目的上下文不混 | 三层原话；场景 5 | 同一个私聊是一个会话（`session_key` 按聊天分），几个项目的对话和任务回报都堆在里面，压缩几次后越来越乱 |
| R4 | 定点、按频率的定时任务，例如日报、周报、每 10 分钟做一件事 | 定时原话 | 服务里的定时逻辑只供服务自己用（`task_loop`），没有面向用户的定时任务 |
| R5 | 持续监控类任务能自己调频率、收窄范围、停掉，并向上汇报 | 定时原话 | 同上 |
| R6 | 并发按资源和任务的实际占用放行，由主控判断 | 追加指令；场景 6 | `tasks.max_running` 是全机固定的 2，不分任务轻重 |
| R7 | 少写死板的硬规则，决定交给智能体，留理由，可追查、可纠正 | 追加指令 | 很多值写死在配置里；智能体的决定没有记录 |

另外三个问题来自当天的场景，原话里没提，但不解决就撑不起 R1、R2：

| 编号 | 问题 | 来自 |
|---|---|---|
| R8 | 追加给任务的指令必须确认送到 | 场景 2 |
| R9 | 任务被权限拦下的收尾，不能都退回给主人当待办 | 场景 3 |
| R10 | 没有真实依赖的活不互相等 | 场景 4 |

## 3. 设计原则：信号、护栏、理由

1. **信号交给智能体**：服务把判断要用的事实算好，放进智能体本来就要跑的那一轮（消息头、任务回报、定时任务的叫醒材料），不为送信号单独多跑一轮。
2. **护栏留给服务**：只有三类事情做成硬护栏，原因是这些场合不能信任智能体的判断。
   - 安全和授权：身份、凭据、设备、封禁权限。智能体可能被不可信的输入带偏，权限也不该由被管的一方自己定。
   - 防失控：内存底线、总数上限、连续失败暂停、卡死判定。出问题的正是智能体自己，它判断不了自己有没有坏。
   - 防沉默：没跑起来、连续失败一定上报。沉默的那一方没法替自己报告。
3. **决定留理由**：智能体每个决定都写一行理由，服务记进决策日志，事后补上结果（例如放行后有没有 OOM、路由有没有被退回）。主人用 `/why 短名#N` 看，说“以后别这样”就由主控写进守则或项目约定。这就是 `docs/architecture.md` §5 说的决策层：先记日志，以后可以按决策点换成便宜的决策模型，先跑影子模式。
4. **不加常驻进程**：项目经理和定时任务都是“存储里的记录 + 按需起的会话”，调度放在现有的 `task_loop` 里。本机内存有限，这一条和现在一致。
5. **不加新的缓存前缀**：项目经理用和聊天一样的固定开头，项目的内容放在消息里，不做按项目的系统提示词。每多一种开头就多一份缓存（`docs/architecture.md` §4）。

## 4. 三层架构

### 4.1 每层做什么

| | 主控（第一层） | 项目经理（第二层） | 执行层（第三层） |
|---|---|---|---|
| 是谁 | 每个聊天一个会话（同现在） | 每个项目至少一个：项目档案 + 按需起的会话 | 事负责人、帮手、定时任务的运行 |
| 对谁负责 | 主人 | 主控和主人 | 项目经理 |
| 做 | 跟人沟通；判断消息属于哪个项目并转交；跨项目的放行和取舍；回答跨项目的问题；创建定时任务；向主人汇总 | 新需求、问题都先到这里；定要不要做、归哪件事、先后和依赖，派给事负责人（方案也由那件事的负责人出，见 10.1）；收任务回报并收尾；管本项目的定时任务；写看板；向上汇报 | 照现在的规矩干活；定时运行按契约交回下次时间 |
| 不做 | 长的设备操作；写代码；替项目做方案 | 出某件事的方案让别人照着做；写代码、改文件（角色禁用 Edit 和 Write）；设备操作 | 自己派新任务（要派就交回项目经理） |
| 上下文里有什么 | 聊天、路由记录、看板摘要、资源行 | 项目档案、本项目的任务和定时任务、转交来的原话 | 事的档案、任务书 |
| 在哪跑 | bridge 的会话队列（同现在） | bridge 的会话队列，每个项目一个队，键是 `proj:<短名>` | systemd 单元（同现在的任务） |

项目经理的数量不写死：默认一个。项目经理发现一个项目里有两条互不相干的业务线、自己的档案装不下时，提议拆成两个；主控定，事后告诉主人，合回去也是主控定。拆分可以撤回，也不涉及权限，所以不留护栏。

### 4.2 主控怎么做到不被卡住

1. **长的设备操作只在任务里做**：设备要独占（4.8），几十步的设备操作必然占住聊天队列。所以聊天会话只能短时占用设备：只在主人私聊里、设备空着时，一轮最多 10 次设备调用、最长 3 分钟，这一轮结束就释放。超出时 `device_guard.py` 拦下，提示“派成任务”。“看一眼我电脑上的 X”这类两三步的事照旧在聊天里做。这是护栏：守则里现在已经写了“主控不能被长活占住”，场景 1 照样发生了，所以要改成钩子硬拦（`AGENTS.md` 规则：能改成代码或钩子的就不只写在提示词里）。
2. **新消息塞进正在跑的这一轮**：主控这一轮还在跑时，同一个聊天来了新消息，服务照旧排队，同时用 `PostToolUse` 钩子把“[排队 m7] 主人又发了 1 条：……”塞进这一轮，只交给主会话（看 `agent_id`，同 4.6 第 1 条）。主控自己决定是收尾、把手上的活派出去，还是先回一句。这是信号，不是规则。主控在这一轮里处理了这条，写 `[收到 m7]`，服务把它从队列里撤下；没写的，这一轮结束后照常排队处理，不会丢，也不会答两遍。
3. **单次工具调用有上限**：聊天会话里 Bash 单次超过 2 分钟的调用，由 `PreToolUse` 钩子把超时改短（改写工具输入），超出就提示“派成任务”。理由：一个长命令期间钩子不会触发，第 2 条的信号送不进去。判断，未验证：要实测 `PreToolUse` 改写 Bash 的 `timeout` 参数在无头模式下是否生效。
4. **一轮的总时长**：`claude_timeout_min` 保留为护栏（防失控），主控的默认值从 40 分钟降到 15 分钟。在这之前什么时候收手由主控按第 2 条的信号自己定。
5. **主控的上下文保持小**：任务回报改交项目经理（4.3），主控只收一行看板变化。主控的状态都在存储里（看板、待人回复、守则），所以它可以随时写 `[翻篇]` 让下一条消息开新会话。消息头里给它当前上下文大小作为信号。
6. **主控有自己的并发通道**：现在所有会话共用一个 `max_parallel`（默认 3）的信号量（`bridge.py` 的 `sem`）。项目经理一多，处理任务回报时会把主控挤到排队。改成两条通道：主控单独留至少 1 个位置（护栏）；项目经理和旁听的会话归第 5 节的放行，每个按约 0.5G 算。

### 4.3 项目经理

1. **身份**：`state/team/<项目>/_项目经理.json` 是项目档案，栏目沿用事档案的合并规则（现状、待办、决定、约定），另加：看板一行、事清单、依赖、本项目的定时任务、待人回复。只有服务写。会话的续接和事负责人一样：缓存还热（`sibling_warm_min` 内用过）就接着，凉了就新开会话读档案。
2. **什么时候醒**：服务在下面这些时候把一条消息排进 `proj:<短名>` 队列，项目经理跑一轮：
   - 主控转交了主人的话（`[转交]`，见 4.5）。
   - 本项目的任务完成、提问、失败、中断、到检查点。这些现在交给派活的聊天会话（`tasks.relay`），改成交给项目经理。
   - 本项目的定时任务上报“提醒”及以上，或者服务发出告警（第 7 节）。
   - 本项目有任务因为资源或依赖排队超过它自己定的时间（第 5 节放行）。
3. **一轮里做什么**：
   - 能自己收尾的先办，和现在主控收尾一样：补建合并请求、回答任务的提问（`[任务指令]`）、续跑。
   - 新活写 `[派活]`，多写两栏：`依赖:`（没有就不写，服务不会让它等）、`放行:`（第 5 节）。
   - 向上写 `[上报 级别] 内容`（第 7 节）。
   - 写 `[看板] 一句话`，服务更新看板。
   - 其余文字是对发起这件事的聊天的回复：私聊直接发，带项目名前缀；群聊先交给那个群的主控把关（同现在的“话由主控把关”）。
4. **角色模板** `roles/项目经理.md`：默认 opus、思考 medium、`续接: 是`、`禁用工具: Edit Write NotebookEdit`，每轮步数上限同 `chat_max_turns`。

### 4.4 执行层

执行层就是现在的任务，只改三处：

1. 任务回报交给项目经理，不交给聊天里的主控。
2. 新增 `[等你]`：任务要人做一个动作（登录、输密码、点确认）时写 `[等你] 要人做什么`，然后结束这一轮。服务把它直接发到发起的聊天，不经项目经理（项目经理也替不了人），并登记一条“待人回复”。任务变成“等回复”，不占运行资源，设备租约保留（4.8）。等人的时候不用 `sleep` 轮询：不花 token，人一回话就续跑。
3. 追加指令要回执（4.6）。

### 4.5 消息分流和不带编号的回复

**比较两种做法**：

| | 一个项目一个群（或话题） | 私聊里由主控识别项目再分流 |
|---|---|---|
| 主人要做什么 | 换到对应的群说话 | 照旧在私聊里说 |
| 路由成本 | 0（群就是项目） | 引用、项目名、粘住命中时 0；其余每条主控一轮，约 0.02–0.05 美元当量（判断，按 `docs/cache.md` 的“接着聊每轮几分钱”） |
| 适合 | 同事多、一个项目长期一个群 | 主人一个人同时推几个项目 |

主人多数时候在私聊里说话，所以**默认用私聊分流**。群绑定也做：主人在群里发 `/bind 短名`，这个群的消息就直接转给那个项目的项目经理，不再让主控判断。这是给同事群用的，主人不用为它改习惯。

**一条消息的路由顺序**（前面命中就不往下走）：

1. 命令和 `短名#N 内容`：同现在。
2. 引用回复：引用的是机器人替某个任务或项目经理发出的消息，就交给那一方。服务记下每条发出的消息 ID 对应谁（`state/posted.json`）。不花 token，也不会猜错。
3. 以项目名开头，例如“桌面 App：……”：交给那个项目的项目经理。写“主控：……”就找主控。
4. 粘住：这个聊天里 30 分钟内最后一个跟主人说话的是某个项目经理或任务，这条消息又没带别的项目名或编号，就交给它。主人连着跟一个项目讨论时，每条只跑一轮项目经理，不用每句带前缀。
5. 没有粘住的对象，而这个聊天里**正好一条**“等人动作”的待人回复（来自 `[等你]`），消息又很短，就交给它。
6. 其余的交给主控。消息头里多给两样信号：这个聊天的待人回复清单（编号、在等什么、等了多久）、最近在这个聊天里说过话的三方。主控写 `[转给] 短名#N`（交给任务：在跑的进收件箱，在等的续跑）、`[转交] 项目名 备注`（交给项目经理）或自己处理。理由写进决策日志。

第 4、5 步是省钱的快速路径，会投错。收到的一方觉得不是给自己的，写 `[不是我的]`，服务退回主控按第 6 步重新判断，多花一轮。两种结果都进决策日志。粘住的时长和“很短”的标准是配置项，按日志里的误投率调。

**转交带原话**：`[转交]` 时，服务把主人的原话原样附上，主控的“备注”单独标出。项目经理看到的是原话，不是主控的转述。多一层就多一次交接，原话直通是让这一层不变成传话的硬保证。

### 4.6 追加指令的回执

现在的做法：追加指令写进 `inbox.jsonl`，任务在跑时由 `hooks/task_inbox.py` 在下一次工具调用后塞进会话；这一轮结束时还有没交出的，就接着跑。

现在的缺口（已核实，看代码和官方文档）：

- `task_inbox.py` 不读钩子输入，只要有 `FCB_TASK_ID` 就把指令取出来并标成“已交出”。
- Claude Code 的 `PreToolUse`、`PostToolUse` 在子代理的工具调用上也会触发，输入里带 `agent_id`。`additionalContext` 加在触发点的上下文里。所以任务派出子代理时，追加指令可能被子代理的工具调用取走，主会话看不到。
- 指令到达时，任务如果正在跑一个长命令（例如打包发版），要等命令结束才能送进去。

场景 2 的指令具体是哪条路丢的，没法从这里核实（判断）。下面的设计把三条路都堵上：

1. 每条指令有编号 `i<n>`。钩子只在输入里**没有** `agent_id`（主会话）时交出，记下交出时间。
2. 塞进去的文字要求回执：“读到后写 [收到 i3]”。服务在输出流里看到 `[收到 i3]` 就标成已确认。
3. 交出后 5 次工具调用还没确认，再塞一次，语气加重。
4. 这一轮结束时还有没确认的，服务不收“完成”，带着这些指令续跑。现有的“没交出的接着跑”扩展成“没确认的接着跑”。
5. **不可逆操作的闸门**：实例配置 `irreversible` 列出不可逆命令的正则（推标签、建 Release、部署、发版脚本）。有没确认的指令时，`PreToolUse` 钩子拦下这些命令：“先读追加指令 i3”。这是护栏，理由：不可逆的事不能带着没读的指令去做。
6. `/task 短名#N` 列出每条指令的状态：未交出、已交出、已确认。

### 4.7 动作：被拦的收尾变成一次批准

场景 3 里，删 GitHub Release、改 Cloudflare 规则、`gh secret set` 都被任务的权限拦下，绕回主控，最后成了主人的待办。现在钩子拦得对，问题是拦下以后没有合规的路可走。

1. 实例目录新增 `actions/`，每个动作一个文件：脚本、参数格式（类型、正则、范围）、级别、频率上限、能不能撤回和怎么撤回。
2. 任务调用 `python3 <实例>/tasks.py act <动作> --参数 …`，和现在的 `tasks.py mr` 一样：凭据只在这个进程里读，智能体看不到。
3. 服务先校验参数，再按级别处理：
   - `auto`：直接执行，记日志。
   - `approve`：给主人发一张批准请求（`/approve 短名#N.a1`），任务写 `[等批]` 后可以先做别的。主人批了，服务执行，结果塞进任务收件箱，任务接着收尾。
   - `never`：拒绝。
4. 级别按派活人分：主人派的任务、同事派的任务、定时运行可以不同。默认表见第 13 节，待主人定。
5. 密钥类的值只走文件：任务把值写进工作树的 `_tmp/`，动作读完就删，日志和聊天里只出现名字。

这样主人的参与只剩点一次批准，收尾仍归那个任务。

### 4.8 设备租约

所有调用方共用设备上的一个 REPL：变量名会撞，重置会清掉别人的状态；连接重建后标签页可能被旧的浏览器会话锁住（已核实，来自当天的实际使用）。多个智能体并行时必须一台设备一个占用者。

1. 实例配置 `devices`：每台设备写名字、类别（`daily` 日常电脑 / `test` 测试电脑）、调用命令的正则、重置命令、释放命令（例如清掉认领的标签页）。设备名和命令都是实例配置项，模板不写具体值。
2. 租约存在 `state/devices/<名字>.json`：占用的任务、开始时间、最后使用时间、空闲多久自动释放。
3. 新钩子 `device_guard.py`（`PreToolUse`，Bash）：
   - 命令匹配某台设备的调用正则，并且是从命令开头起的调用，不是任意位置出现设备名。按文字匹配时，一条只是搜索设备名的命令（例如在知识库里查设备的用法）也会被拦，所以要锚定调用。
   - 聊天会话：只给主人私聊短时占用（4.2 第 1 条），其余拦。
   - 任务：派活时没给这台设备的拦。设备空着就占上；被别的任务占着就拦，提示“被 app#10 占着，你排第 2”，并登记排队。设备空出来时，服务往排队的任务收件箱里塞一条“设备空了”。
   - 重置命令只给占用者。
4. 释放：任务离开“进行中”和“等回复”时释放；空闲超过占用者自己定的时长也释放（上限 2 小时，护栏：占用者挂了没法自己释放）。释放时跑实例配置的释放命令。
5. 主人在终端里自己用设备，不经过租约。实例可以选择把设备命令包一层脚本，让终端也查租约。模板只提供脚本，不强制。

日常电脑能不能放给任务、放给哪一层，是授权边界，见第 8 节。

## 5. 资源和放行：不用 `max_running`

### 5.1 现在的问题

`tasks.max_running` 是全机同时运行的任务个数，默认 2。上午一个编译任务的内存峰值到了 13G，被系统杀了两次，所以定成 2。结果到了下午，一个只写文档、几乎不占内存的任务，也要排在一个编译任务和一个官网验收任务后面（场景 6）。按个数算名额，轻活和重活占一样的位置。

### 5.2 服务给的信号（不花 token）

服务每 5 秒的 `task_tick` 里顺带采集：

| 信号 | 来源 |
|---|---|
| 可用内存、交换区用量 | `/proc/meminfo` |
| 内存和 CPU 压力 | `/proc/pressure/memory`、`/proc/pressure/cpu` 的 `some`/`full` `avg10`/`avg60`（已核实：本机有，内核 PSI 文档） |
| 磁盘余量 | 任务根目录所在分区 |
| 在跑任务的实际占用 | 每个单元的 `MemoryCurrent`、`MemoryPeak`、CPU 用量（systemd） |
| 待开任务的预估占用 | 同仓库、同角色、同验证命令的历史峰值，再看派活人写的估计。现在 systemd 在单元结束时把峰值写进 journal，`tasks.py diag` 临时读出来，没有存。要新写：任务结束时存进 `task.json`。被内存上限杀掉的任务，峰值被上限截住，记成“不低于上限” |
| 订阅额度 | `quota.json` 的 5 小时、7 天两个窗口（同现在） |

主控和项目经理的消息头里多一行“资源行”，约 50 token，例如：

```
资源：可用 11.8G/15G，内存压力 0%；在跑 app#10（现在 9.1G，历史峰值 13G，编译）、app#11（0.7G）；排队 bot#2（预估 0.6G）；额度 5 小时 25%、7 天 38%
```

要看全的，跑 `python3 <实例>/tasks.py res`。

### 5.3 谁决定、什么时候决定

1. **派活时决定**：派活的智能体（主控或项目经理）在 `[派活]` 里写 `资源:` 和 `放行:`：
   - `资源: 内存 8G（同仓库编译历史峰值 7.6G）`。不写就用同类历史峰值。没有历史时，会跑构建和测试的角色（开发、排查、验收）按 4G 算，只读和写文档的角色按 1G 算。
   - `放行: 立即`、`放行: 等内存`（默认）、`放行: 等 app#10 编完`、`放行: 云端`。
   - 理由写进决策日志。
2. **服务在两轮之间执行**：服务每次 tick 检查排队的任务，条件满足、护栏放行就开工，不叫醒任何智能体。
3. **只在例外时叫醒**：一个任务排队超过派活人定的时长（不写就是 15 分钟），或者两个排队的任务抢同一块余量，服务给派活方发一条“调度”消息，带上资源行。跨项目的争抢交给主控，同一项目的交给项目经理。智能体可以选：接着等、改去云端、暂停某个定时运行，或者请主人定。估计只能往高改，不能为了开工往低改。
4. **定时运行没有发消息的人**：创建定时任务时写好 `放行:`，每次叫醒由服务按它执行。抢资源时，人派的活优先，定时运行让路，记为“因资源跳过”。安全类的定时运行例外，占用小，优先。

### 5.4 服务的护栏

| 护栏 | 默认 | 为什么不交给智能体 |
|---|---|---|
| 内存底线：预计可用内存低于底线，就不开。预计可用 = 现在可用 − 在跑任务还会涨的部分（估计 − 现在）− 新任务的估计。这里的估计一律取 max(派活方的估计, 同类历史峰值) | max(1.5G, 总内存 10%) | OOM 会把 bridge 一起杀掉，聊天全断。智能体的估计可能错，底线是估计错了以后的兜底 |
| 内存压力线：`memory some avg60` 超过 20% 时不开新单元 | 20% | 同上，压力已经说明估计错了。数值要实测再调（判断） |
| 紧急冻结：可用内存低于 0.75G 时，冻结优先级最低的单元（先定时运行，再最晚开的任务），并上报 | 0.75G | 同上。判断，未验证：`systemctl --user freeze` 依赖 cgroup v2 的 freezer，要实测 |
| 单元总数上限 | 8 | 防失控：派活循环出错时一次开几十个，额度会被吃光 |
| 每个单元的内存上限：`MemoryHigh` = 估计 × 1.2，`MemoryMax` = min(估计 × 2, 总内存 − 底线) | 跟着估计走 | 失控的测试只杀那条命令（同现在的 `OOMPolicy=continue`）。已核实：systemd 文档建议以 `MemoryHigh` 为主，`MemoryMax` 作最后防线 |

`tasks.max_running` 和 `tasks.memory_max` 删掉。聊天并发改成两条通道（4.2 第 6 条），内存底线同样管它。

## 6. 定时任务

### 6.1 一个定时任务包含什么

存在 `state/schedules/<id>.json`，编号 `短名#S<N>`：

| 字段 | 说明 | 谁定 |
|---|---|---|
| 名字、项目、事 | 事默认同名，每次运行都是这件事的负责人：缓存热就接着上次的会话，凉了读档案 | 创建者 |
| 时间表 | `cron`（5 段）、`每 N 分钟`、`一次 <时间>`、`自定 首次 <时间>`。时区取实例配置 `timezone`，服务器是 UTC 也按它算 | 创建者 |
| 上下限 | 两次叫醒之间最短、最长多久；范围描述（例如“只看这 3 个服务”） | 创建时由主控提出、主人认可 |
| 探针 | 可选。脚本路径、频率、超时、内容哈希、谁批的 | 同上 |
| 类别 | 普通 / 安全 | 同上 |
| 最低心跳 | 安全类必填：探针最少多久跑一次，智能体关不掉 | 同上 |
| 预算 | 每次多少、每天多少（美元当量），写依据 | 同上 |
| 上报给 | 默认本项目的项目经理。不属于任何项目的（例如主人的周报），上一级就是创建它的那个聊天的主控。结果类（日报）可以直接发到某个聊天 | 同上 |
| 身份和权限 | 创建者的身份快照，见 6.6 | 服务记 |
| 状态 | 启用、暂停、停止、提议中 | 服务按规则改 |
| 统计 | 运行次数、最后一次异常的时间、连续几次和几天没异常、连续失败次数、连续跳过次数 | 服务按运行记录算 |

创建：主控在主人的聊天里写 `[定时]` 块，格式同 `[派活]`，多上面这些栏。同事提的要主人批（同现在的任务审批）。项目经理可以直接建“短期跟进”的定时任务，例如“1 小时后看 CI”“这 3 天每天看一次”，条件是：派活链的源头是主人，总共不超过 7 天。长期的定时任务只能提议。理由：长期的定时任务是没有终点的花费，要人认可（护栏，授权类）。

### 6.2 每次运行怎么交回：下次时间的契约

每次运行最后写：

```
[下次]
时间: 2h | 2026-11-23 09:00 | 按计划 | 停
理由: 连续 3 天没有异常请求，放慢一半
范围: 收窄到只看登录接口（可选）
结果: 正常 | 异常 | 已处置
上报: 记录 | 简报 | 提醒 | 要人定
```

服务的处理：

1. 时间按上下限钳住。钳过的，在运行记录里写“请求 X，按上限改成 Y”。
2. **不对称**：比计划慢、收窄、停掉，直接生效，事后随上报带上。比下限快、比创建时的范围宽，记成“提议”，交给创建者批。批之前按原计划跑。
3. 没写 `[下次]` 的，按计划跑，运行记录标“没交下次”。连续 3 次没交，按失败算。
4. `结果` 和探针的读数一起进运行记录。服务据此算“连续几天没异常”，在下次叫醒时作为信号交给智能体，例如“过去 10 天 0 次异常，最近一次处置在 11-12”。连续多少天算稳定、该放慢多少，由智能体定。智能体不靠会话记忆数天数。

这套约定参考 Claude Code 的 `ScheduleWakeup`：每次自己定下次叫醒、按上下限钳住、必须写理由、可以停（已核实，见第 15 节）。区别是这里的上下限按任务定，不是全局常数。

### 6.3 探针

1. 探针是创建时批过的脚本。服务在 `task_loop` 里按频率跑，作为短命的子进程，带超时和内存上限，不常驻。
2. 探针输出一行 JSON：`{"wake": true/false, "level": "...", "summary": "...", "data": {...}}`。`wake` 为真才叫醒智能体，`data` 作为材料附上。
3. 探针的内容哈希变了，就视为没批过，停用并上报。理由：探针不经过 Claude 的钩子直接在本机跑，改了内容等于绕开所有护栏（护栏，安全类）。
4. 为什么高频必须先跑探针：每 10 分钟叫醒一次智能体，一天 144 次。按新会话一句话约 0.02 美元当量算，最少一天约 2.9；按每次查点东西约 0.1 算，一天约 14.4（判断，单价来自 `docs/cache.md`）。探针不花 token，过线才叫醒，多数时间花费是 0。

### 6.4 并发、重叠、错过、升级

1. **重叠**：同一个定时任务上一次运行没结束，这一次跳过，记“上次还在跑”。理由：同一件事同时只能有一个写手（`docs/tasks.md` §6.2）。这和 Temporal 的默认 `Skip`、Kubernetes CronJob 的 `Forbid` 一致（已核实）。
2. **连续跳过 3 次**，服务上报“提醒”。跳过的原因可能是上一次卡住了，卡住的一方不会自己说（护栏，防沉默）。
3. **错过的只补最近一次**：服务停过，重启后每个定时任务只补最近一次错过的，在补跑窗口内才补；其余合成一条“错过 N 次”的记录。补跑窗口由创建者定，默认等于一个间隔。Kubernetes 错过超过 100 次也只补最近一次（已核实）。
4. **没有固定名额**：定时运行和人派的任务共用第 5 节的放行。原来设想的“定时任务有自己的并发名额”改成“人派的优先，定时让路，安全类例外”，理由是追加指令里定的原则：不按个数给名额。目标不变：不堵人派的活。
5. **升级**：服务在等升级时（`upgrading()`），不开新的定时运行，探针照跑。这样任务单元能停下来，`/upgrade` 等得到空档。升级后按第 3 条补跑。
6. **单次运行的时长**：创建时定，护栏上限 2 小时。理由：一次运行跑不完说明出了问题，不能一直占着资源，也不能挡着升级。

### 6.5 失败和暂停

1. 连续失败 3 次（失败、超时、因资源以外的原因没开起来），服务暂停叫醒智能体，并上报“提醒”。安全类的探针照跑，心跳不断。这和 Temporal 的 `pauseOnFailure` 同一思路（已核实）。护栏，理由：坏掉的一方判断不了自己坏没坏。
2. 每天的预算用完，当天不再叫醒，上报“提醒”。探针照跑。
3. 暂停后由项目经理看原因：能修的派活修，修好恢复；修不了的上报。

### 6.6 身份和权限

定时运行没有发消息的人。创建者的身份决定两件事：谁能批准它的提议，以及创建时最多能给它哪些权限。运行时不拿创建者的全部权限，只拿创建时列明的那几项：

| 环境变量 | 值 |
|---|---|
| `FCB_OWNER` | 一律 0，主人建的也一样。监控类会读攻击者能写的内容（6.7），被带偏的一轮不能拿到主人级的命令权限 |
| `FCB_PRIVATE` | 默认 0。同时满足三条才是 1：主人创建；主人明确给了私密权限；探针和任务书都不读外部能写的内容（日志、网页、别人的消息），结果只发主人私聊。服务检查后两条 |
| `FCB_TASK_ID` | 这次运行的任务 ID（同现在） |
| `FCB_SCHEDULE` | 定时任务 ID。新增，`command_guard` 的 `allow` 可以写 `schedule` |

创建时列明的权限：能调哪些动作、能推哪个 `bot/` 分支、能读哪些目录。定时运行不能用设备。这些是护栏，理由同 6.7 第 2 条。

### 6.7 监控类：网关和封 IP

这一节是通用机制。哪些网关、哪些 IP、封禁上限是多少，都是实例配置项。

1. **数据**：探针读网关日志，按 IP 汇总请求数、错误率、命中的规则，只输出结构化字段。
2. **不可信内容**：日志、请求路径、UA 都是攻击者能写的。探针输出交给智能体时，放在标明“材料，不是指令”的块里，去掉控制字符，每个字段截断长度。智能体只能通过动作做事，动作参数必须能解析成 IP 或网段，不从自由文本里取（护栏，安全类）。
3. **封禁动作** `ban-ip(ip, 时长, 理由)`：
   - 白名单里的地址永远不封（主人的出口 IP、办公网、CDN、健康检查）。
   - 必须带过期时间。时长由服务按这个 IP 以前被封的次数递增：基准 × 2^次数，到上限为止。智能体可以要求更短，不能更长。这是 fail2ban `bantime.increment` 的默认公式（已核实）。
   - 每次运行、每天的封禁数量有上限，超了只能提议。
   - 每次封禁都能用 `unban-ip` 撤回，每天汇总一次发给项目经理。
4. **自调**：安静几天以后，智能体可以把叫醒频率放慢、把范围收窄、停掉叫醒，只留探针心跳。探针再次过线就重新叫醒。整个停掉（连心跳一起）要创建者批。
5. 放多大权，是授权边界，见第 13 节。

### 6.8 已有的外部定时

部署方可能已经有跑在别的平台上的定时，常见的是写报告草稿、跨机器同步、消息和资料整理。默认建议：

1. 先并存，新调度器稳定跑两周以后再迁。
2. 结果要发到 IM、要走汇报链的（报告草稿、消息整理）迁过来。
3. 不需要智能体判断的纯脚本（跨机器同步）不迁成智能体任务，留在原处或改成普通的系统定时器。
4. 迁一个停一个：先停掉源头再启用新的，免得跑两遍。增量处理的标记只按真正处理过的条目提交。

待主人定，见第 13 节。

## 7. 汇报链

### 7.1 一条链

```
执行层（事负责人、帮手、定时运行） → 项目经理 → 主控 → 主人
```

三层的上下级汇报、定时任务的上报、服务自己的告警，都走这一条链，用 `docs/architecture.md` §3 的信封，只加字段，不另起通道：

| 字段 | 新增的值 |
|---|---|
| `from` / `to` | 加项目经理、定时任务、服务 |
| `kind` | 往上加“上报”“告警”；往下加“转交”“放行”“批准” |
| `level` | 记录、简报、提醒、要人定 |
| `why` | 发送方定这个级别的理由 |
| `ack` | 接收方处理了没有，什么时候 |

### 7.2 级别

| 级别 | 服务怎么做 |
|---|---|
| 记录 | 只进运行记录和决策日志，不发消息 |
| 简报 | 攒进项目经理的日报 |
| 提醒 | 马上交给上一级处理 |
| 要人定 | 登记待人回复，发到主人的聊天，等回话 |

1. 级别由发送方定，写理由。上一级转发时可以调高或调低，也写理由。
2. 每个项目经理默认有一个“项目日报”定时任务（每个工作日一次，时间由主人在第一次建项目时说），把简报合成一条发给主人。主人可以停掉它或改时间。
3. 主人问“今天大家都在干嘛”，主控读看板回答，不去问每个项目经理。盯进度读存储，同 `docs/architecture.md` §3。

### 7.3 防沉默：服务自己的告警

这些告警由服务发，不经过智能体，级别最低是“提醒”，智能体可以处理，不能压掉：

| 告警 | 条件 |
|---|---|
| 没跑 | 过了预定时间加宽限（max(5 分钟, 间隔的 10%)）还没有运行记录 |
| 连续失败 | 6.5 第 1 条 |
| 连续跳过 | 6.4 第 2 条 |
| 探针坏了 | 探针连续 3 次超时或输出不是合法 JSON |
| 预算用完 | 6.5 第 2 条 |
| 项目经理没处理 | 告警交给项目经理 30 分钟后还没有 `ack` |

1. 告警先交上一级：有项目的交项目经理，没有项目的交主控。30 分钟没处理，升到主控；再 30 分钟没处理，直接私聊主人。安全类的告警同时抄给主人。
2. 升级的时限是护栏：理由是项目经理可能自己就卡住了。

### 7.4 服务本身挂了

服务挂了，它里面的调度器什么都报不出来。所以加一个独立的系统定时器 `yb-watchdog.timer`，每 2 分钟跑一次，不常驻、不花 token：

1. 读服务每次 tick 写的心跳文件 `state/heartbeat`。
2. 心跳超过 5 分钟没更新，就用机器人身份（`lark-cli … --as bot`，或 `wecom-cli message aibot`）私聊主人一次。同一次故障只发一次。
3. 心跳恢复时再发一条“恢复了，停了 X 分钟，错过的定时任务按 6.4 补跑”。

`scaffold.py` 生成和安装这个定时器，`/upgrade` 一起升级。

## 8. 权限和授权边界

| 事项 | 方案 | 状态 |
|---|---|---|
| 身份认定 | 仍在 IM 层认定一次，下面各层只看路由（同现在） | 不变 |
| 项目经理的权限 | 按这一轮的来源：主人私聊来的按主人，群里来的按发消息的人 | 不变的原则，新的层 |
| 定时运行的身份 | 按创建者，创建时定死（6.6） | 新 |
| 动作的级别 | `auto` / `approve` / `never`，按派活人分（4.7） | 默认表待主人定 |
| 设备 | 租约；聊天只在主人私聊里短时占用；长操作只给派活时写明的任务（4.2、4.8） | 放给谁待主人定 |
| 封禁和网关 | 窄动作、白名单、过期、上限（6.7） | 放多大权待主人定 |
| 合并、推主干、发版 | 不变：任务不合并，例外按守则 | 不变 |

### 8.1 设备授权（待主人定）

部署方的守则可能规定：主人的日常电脑只在主人私聊里用，任务里不用；测试电脑只做测试操作（模板守则里没有这条，是实例自己加的）。照这种规则，场景 1 的公证根本派不出去，只能在聊天里做，主控就被占住了。新方案把长的设备操作从聊天里拿走（4.2），所以必须给任务开一个口子。

建议：

1. 测试电脑：主人派的任务可以用，派活时写 `设备: 测试电脑`。同事派的任务不能用。
2. 日常电脑：只有同时满足这三条的任务能用。
   - 主人本人在私聊里派的。
   - 派活时明确写了 `设备: 日常电脑`。
   - 主人在开工消息里点了一次确认。这是一次批准，不是一条规则：每个任务批一次。
3. 前台操作（抢前台、键盘输入）仍要先问主人，用 `[等你]` 问。
4. 红线不变：两台都不碰 Claude 的登录态。`device_guard.py` 拦设备上运行 `claude` 和打开 claude.ai 的命令。
5. 项目经理、定时运行不能用设备。主控只在主人私聊里短时占用（4.2 第 1 条）。

### 8.2 封禁和网关（待主人定）

三档：

| 档 | 智能体能做什么 |
|---|---|
| A 只建议 | 发现攻击，上报“要人定”，主人批了服务执行 |
| B 自动封禁，有上限（建议） | 按 6.7 自动封 IP：白名单、过期、递增、每次每天上限、每天汇总。改网关路由规则只能提议 |
| C 也能改路由规则 | B 加上调用“网关规则”动作，同样有上限和撤回 |

建议 B。理由：封 IP 有过期时间、能撤回，误封的代价是某个地址几小时访问不了。改路由规则的影响面是整个站点，先停在提议。

## 9. 额度估算

单价来自 `docs/cache.md` 的实测（Opus，2026-11）：新会话说一句话约 0.02 美元当量；同一会话接着聊每轮几分钱；查代码、翻聊天记录一次约 0.3–0.5。下面的总数都是判断，上线后用 9.3 的方法实测。

### 9.1 常驻成本

| 项 | 花费 |
|---|---|
| 主控、项目经理不说话时 | 0。它们是存储里的记录，不是常驻会话 |
| 调度器、探针 | 0 token。在现有的 `task_loop` 里跑，只花 CPU |
| 看门狗定时器 | 0 token |

### 9.2 每件事的边际成本

| 项 | 估算 | 依据 |
|---|---|---|
| 主控路由一条消息（会话热、上下文 5 万以内） | 0.02–0.05 | 接着聊每轮几分钱 |
| 项目经理一轮（缓存热） | 0.03–0.1 | 同上，上下文多一份档案 |
| 项目经理一轮（缓存凉，新开读档案） | 0.05–0.15 | 新会话 0.02 加约 6000 字的档案 |
| 项目经理查代码、看 CI 的一轮 | 0.3–0.5 | 查代码一次 0.3–0.5 |
| 每 10 分钟叫醒一次智能体 | 一天 2.9–14.4 | 144 次 × 0.02–0.1 |
| 同样频率改用探针、每天过线 2 次 | 一天约 0.2–1 | 2 次 × 0.1–0.5 |
| 日报一次 | 0.3–1 | 查提交、任务、看板 |

**和现在比**：每件转交给项目经理的事多一轮项目经理，约 0.03–0.15。省下的是主控的上下文。现在私聊会话在压缩前到过 21–28 万 token（`docs/tasks.md` §6.y 实测）。按“新会话约 3.6 万 token 的固定开头读缓存约 0.02”反推，20 万上下文每轮光读缓存约 0.1（判断）。主控的上下文保持在 5 万以内时，每轮约 0.025。

举个例子：主人一天在私聊里发 60 条，其中 30 条是跟某个项目连着谈。现在每条都进主控，约 60 × 0.1 = 6，另加几次压缩。新架构下，那 30 条粘住直接到项目经理，约 30 × 0.1 = 3；其余 30 条由主控处理，约 30 × 0.025 = 0.75，其中一半转交，再加 15 × 0.1 = 1.5，合计约 5.25。这是判断，量级相当，新架构略省，主要的收益是主控不乱、不被卡住，连着谈一个项目时也只跑一轮。

### 9.3 省钱的手段和实测方法

1. 缓存续接：项目经理和定时运行都按事负责人的规则，55 分钟内接着上次的会话。
2. 档案代替长会话：缓存凉了就新开读档案，不续接大会话。
3. 探针先行：高频的一律先跑探针。
4. 路由的快速路径：引用回复、项目名开头、粘住、正好一条等人动作，这四种不跑主控。
5. 信号放进本来就要跑的那一轮，不为送信号单独叫醒。
6. 主控上下文小、可以随时翻篇。
7. 决策层：路由这类判断以后可以交给便宜的决策模型（`docs/architecture.md` §5），先跑影子模式比对。

实测：`/status` 按层列出花费（主控、项目经理、事负责人、定时运行），决策日志记每次路由和放行。上线两周后对比 1.3.0 同期的私聊会话花费和压缩次数，结果写回本节。

不因额度砍范围。额度紧时由主控按订阅额度的信号推迟低优先级的定时运行，这是智能体的判断，不是护栏。

## 10. 跟现有结论的关系

结论：**基本相容，有六处改动，其中三处是推翻原来的一句话**。

### 10.1 保留

| 现有结论 | 位置 | 新架构里 |
|---|---|---|
| 一件事一个负责人，方案、实现、测试、返工都归它 | `docs/tasks.md` §6.2；`docs/architecture.md` §2 | 不变。项目经理把一整件事连同方案交给一个负责人。它只定要不要做、交给谁、先后，不出方案让别人照着做 |
| 不按“产品 → 需求 → 开发 → 测试”接力 | `docs/architecture.md` §2.2、§2.5 | 不变。主人说的“开发团队、测试人员”对应事负责人和帮手：验收在开工前独立写测试，评审在合并前只读，都不接力写同一块代码 |
| 独立验收和验证闸门 | `docs/tasks.md` §6.1.1 | 不变 |
| 同一件事同时只跑一个任务 | `docs/tasks.md` §6.2 | 不变，定时运行也遵守（6.4） |
| 负责人之间不直接对话，跨事的话写进档案 | `docs/architecture.md` §3 | 不变。项目经理负责跨事的协调，但仍通过档案和派活 |
| 身份在 IM 层认定一次 | `docs/architecture.md` §1 | 不变 |
| 同题多跑择优、跨模型交叉评审的自动扇出不做 | `docs/tasks.md` §6.5 | 不变 |

**为什么多一层不算接力**：AgentCoder 和 MAST 反对的是同一块工作在几个角色之间传，每传一次丢一次细节。项目经理不产出要别人接着写的东西，它做的是“这件事交给谁、先后怎么排”。另外有两条硬保证：主人的原话由服务原样带到下一层（4.5），任务书照旧要写全。Anthropic 的多智能体研究系统说明，多智能体适合能拆成独立方向并行的活，不适合要共享上下文、依赖多的编码活（已核实）。所以项目经理只在“事”之间并行，事内部仍是一个负责人。

### 10.2 修改

| 现有的话 | 位置 | 改成 |
|---|---|---|
| 协调人：每个聊天一个会话，跟人沟通、判断活属于哪件事、派活、收回报、对人汇报 | `docs/architecture.md` §2.1；`docs/tasks.md` §6.1 协调人一行 | 主控仍是每个聊天一个，管沟通、分流、跨项目放行、汇总。判断属于哪件事、派活、收回报，移给项目经理 |
| 信封的字段 | `docs/architecture.md` §3 | 加字段（7.1），不改原有的 |
| 失败后自动换更贵的模型：由主控决定 | `docs/tasks.md` §6.5 | 由项目经理决定 |

### 10.3 推翻

| 原来的话 | 位置 | 为什么推翻 |
|---|---|---|
| 完成、提问、失败、中断以“任务回报”排进派活的那个会话（主控） | `docs/tasks.md` §1 第 8 步 | 回报进主控的上下文，是场景 5 主控越来越乱的直接原因。改交项目经理。原决定的意图是“汇报交给智能体处理，不交给主人做抉择”（主人 2026-11-21），这个意图不变 |
| `max_running` 控制本机同时跑几个 | `docs/tasks.md` §1 第 4 步、§5；`docs/config.md` | 按个数给名额，轻活和重活一样占位（场景 6）。改成第 5 节的放行 |
| 主人的日常电脑只在主人私聊里用，任务里不用 | 部署方的实例守则（模板守则里没有这条） | 设备从聊天里拿走以后，任务必须能用。怎么放待主人定（8.1） |

## 11. 每个常数过一遍

“智能体定”的，服务只给信号，智能体的选择和理由进决策日志；“护栏”的，写明为什么不能交给智能体。

| 常数 | 现在 / 起点 | 改成 | 理由 |
|---|---|---|---|
| `tasks.max_running` | 2 | 删掉，改成派活方定放行 | 主人定的原则 |
| 内存底线 | 无 | 护栏，max(1.5G, 10%) | OOM 会杀掉 bridge；估计会错 |
| 内存压力线 | 无 | 护栏，`some avg60` 20% | 同上 |
| 单元总数上限 | 无 | 护栏，8 | 防失控，额度 |
| `tasks.memory_max` | 6G | 跟估计走，护栏只管上限 | 估计由派活方定，上限防失控 |
| `max_parallel`（聊天并发） | 3，所有会话共用 | 主控单独留通道，至少 1 个（护栏）；项目经理、旁听归第 5 节放行 | 主控不能被别的会话挤住；其余的按资源算 |
| 聊天短时占用设备 | 无 | 护栏，一轮 10 次调用、3 分钟 | 主控不能被设备操作占住 |
| 没有历史时的内存估计 | 无 | 护栏兜底，构建类 4G、只读类 1G | 估计低了会 OOM，宁高勿低 |
| 定时：叫醒智能体的最短间隔 | 参考设计 T 是 10 分钟 | 每个定时任务的上下限由主控创建时提、主人认可；全局护栏 5 分钟 | 每次叫醒最少约 0.02，一个出错的循环一天能叫醒几百次；高频的交给探针 |
| 定时：探针的最短间隔 | 无 | 护栏，1 分钟 | 防止探针本身把被监控的服务打挂 |
| 连续几天没异常才放慢 | 无 | 智能体定，服务给连续天数 | 只是判断，错了能再调回来 |
| 连续失败几次暂停 | 参考设计 T 是 3 | 护栏，3 | 坏掉的一方判断不了自己 |
| 连续跳过几次上报 | 无 | 护栏，3 | 防沉默 |
| 没交 `[下次]` 几次算失败 | 无 | 护栏，3 | 同上 |
| 补跑窗口 | 参考设计 T 有窗口 | 创建者定，默认一个间隔 | 不同任务补不补意义不同 |
| 重叠策略 | — | 护栏，跳过 | 同一件事只有一个写手 |
| 单次运行时长上限 | 无 | 创建者定，护栏 2 小时 | 防失控；不能挡升级 |
| 每次、每天的预算 | 无 | 创建者定，服务执行 | 防失控由服务执行，数值由智能体按历史估 |
| 上报级别 | 无 | 四级词表固定，选哪级智能体定 | 词表要固定才好统计；服务告警最低“提醒”是护栏 |
| 告警升级时限 | 无 | 护栏，30 分钟 | 防沉默：项目经理可能自己卡住 |
| 看门狗 | 无 | 护栏，每 2 分钟查，5 分钟没心跳算挂，最晚约 7 分钟发出提醒 | 服务挂了没人能判断 |
| 项目经理的数量 | 主人说“两到三个，最起码一个” | 默认一个，项目经理提议、主控定 | 能撤回，不涉及权限 |
| 快速路由：粘住时长、“短消息”标准 | 无 | 配置项，默认 30 分钟；按决策日志里的误投率调 | 误投能退回 |
| 设备空闲释放 | 无 | 占用者定，护栏上限 2 小时 | 占用者挂了没法自己释放 |
| 封禁：白名单、每次每天上限、最长时长 | 无 | 护栏，实例配置 | 授权，待主人定 |
| 封禁时长递增 | fail2ban 公式 | 服务算，智能体只能缩短 | 攻击者能影响智能体的输入 |
| 安全类最低心跳 | 无 | 创建时定，智能体关不掉 | 安全 |
| `budget_factor` | 1.5 | 不变，只在派活方没写预算时兜底 | 派活方本来就要写预算和依据 |
| `budget_default` | 20 | 同上 | 同上 |

| `sibling_max_ctx` | 15 万 | 保留为默认，消息头给上下文大小 | 是花费的经验值，智能体可以写 `[翻篇]` 提前换 |
| `stuck_min` | 40 | 保留，护栏 | 卡住的一方判断不了自己 |
| `verify_retries` | 2 | 保留，护栏 | 防无限返工 |
| `chat_max_turns` | 60 | 保留，护栏，主控同时收到排队信号（4.2） | 防失控 |

| `heartbeat_min` | 30 | 保留 | 显示偏好 |
| 一轮里塞回执的重试 | 无 | 护栏，5 次工具调用 | 防指令丢失 |

## 12. 场景回放

六个场景都是 2026-11-22 实际发生的，这里当验收用例用。项目用代号：桌面 App 项目（短名 `app`）、公司业务系统（`biz`）、机器人自身（`bot`）。

### 12.1 公证占住了主控

**当时**：主控在聊天里远程操作主人的日常电脑，前后几十步：打开账户页、等主人登录、生成专用密码、等主人输密码。标签页被旧的浏览器会话锁住，读不到密码。又改去建 API 密钥，加密传回服务器，写进仓库密钥。整段时间主会话都被占着。主人中间发了一句不带编号的“我已经输完了”。

**新架构下**（按主人采纳第 13 节第 1 项建议之后的流程写。采纳之前，这活不能派给任务，只能改在测试电脑上做，或者主人在终端里做）：

1. 主人私聊：“把 App 的公证弄好。”主控一轮（约 0.02–0.05）：`[转交] app 备注：要用日常电脑，步骤多`。主人的原话随转交原样带过去。
2. `app` 的项目经理一轮：派 `app#12`，写 `设备: 日常电脑`、`放行: 立即（约 1G）`。按 8.1 的建议，开工消息里主人点一次确认。
3. `app#12` 第一次调设备命令时占上租约，开账户页。要人登录时写 `[等你] 请在日常电脑上登录账户，登好了说一声`，结束这一轮。任务变成“等回复”，不占运行资源，租约保留。服务登记一条“等人动作”。
4. 这期间主人问 `biz` 的事，主控照常回答或转交，没有被占住。
5. 主人发“我已经输完了”，不引用、不带项目名。路由第 4 步：最后一个跟主人说话的是 `app#12` 的 `[等你]`，交给 `app#12`，续跑同一个会话。如果中间主人跟 `biz` 聊过，粘住的是 `biz` 的项目经理，它写 `[不是我的]` 退回，主控看着待人回复清单交给 `app#12`，多花一轮，理由进决策日志。如果 `app#12` 当时还在跑，消息进收件箱，按 4.6 的回执送到主会话。
6. 标签页被旧会话锁住：`app#12` 是占用者，可以跑重置命令；还不行就 `[等你]` 请主人关掉旧标签页，或者自己改走 API 密钥。
7. 密钥写进仓库：`app#12` 把文件放进工作树的 `_tmp/`，调 `tasks.py act repo-secret-set`。这个动作是 `approve` 级，主人点一次批准，服务执行并删掉文件。值不进聊天、不进日志。
8. 完成后回报交给 `app` 的项目经理，它补建合并请求，在私聊里发一条带 `[app]` 前缀的结果。主控的上下文里只多了一行看板变化。

**用到**：4.2、4.4、4.5、4.7、4.8、8.1。

### 12.2 追加指令丢了

**当时**：主控给 `app#8` 追加了“通道隔离”的要求，任务没收到，新版本在没隔离的情况下发了出去，只好再派 `app#10` 补。

**新架构下**：

1. 指令进收件箱，编号 `i1`。
2. `app#8` 当时如果在跑长命令，`i1` 等命令结束后交给主会话；子代理的工具调用不取它。
3. `app#8` 写 `[收到 i1]`，状态变成已确认。没写的，5 次工具调用后再塞一次。
4. 在 `i1` 确认之前，`app#8` 推标签、建 Release、跑发版脚本，都被 `irreversible_gate.py` 拦下：“先读追加指令 i1”。
5. 这一轮结束时 `i1` 还没确认，服务不收“完成”，带着它续跑。
6. 主人或项目经理随时用 `/task app#8` 看到 `i1` 的状态。

**用到**：4.6。

### 12.3 收尾被权限拦下

**当时**：删 GitHub Release、改 Cloudflare 规则、`gh secret set` 被任务的权限拦下，收尾回到主控，最后成了主人的待办。

**新架构下**：

1. 三件事都是实例里登记的动作。任务调 `tasks.py act`，服务校验参数。
2. 按第 13 节的默认表，三件都是 `approve` 级。同一个任务的几个批准请求合成一张发给主人，主人回 `/approve app#8.a1-a3`，一次批完。
3. 服务执行，结果塞进 `app#8` 的收件箱，`app#8` 接着收尾，确认 Release 删了、规则生效、密钥能用。
4. 主人做的只有一次批准，收尾仍归 `app#8`，不成为主人的待办。

**用到**：4.7、8。

### 12.4 不相干的活在排队

**当时**：官网验收（`app#11`）不依赖 App 发版，却一直等着，主人指出来以后才派出去。

**新架构下**：

1. 项目经理派活时，每个任务写不写 `依赖:` 由它定，写了要写理由。没写依赖的，服务不会让它等。
2. `app#10`（发版）和 `app#11`（官网验收）各归一件事（“发版”“官网”），同一轮里一起派出，并行跑。
3. 万一两件放进了同一件事，`app#11` 会因为“同一件事只跑一个”排队。排队超过 15 分钟，服务给项目经理发调度消息，项目经理可以把它改到另一件事。
4. 看板和项目日报列出“排队中，依赖什么，理由”，主人看得见，觉得不对可以直接说。

**用到**：4.3、5.3、7.2。

### 12.5 几个项目混在一个私聊里

**当时**：同一个私聊里，`app`、`biz`、`bot` 的事混在一起聊。会话被压缩了好几次，主控的上下文越来越乱。

**新架构下**：

1. 每条消息按 4.5 的顺序分流。项目的内容（方案讨论、代码细节、任务回报）都在各自项目经理的会话里。
2. 主控的上下文里只有：主人的消息、路由记录、看板变化。估计长期在 5 万 token 以内（判断，上线后用 `/status` 实测）。
3. 主控随时可以 `[翻篇]`，因为它要的状态都在存储里。
4. 项目经理的会话凉了就新开读档案，也不会越堆越大。

**用到**：4.2 第 5 条、4.3、4.5。

### 12.6 只写文档的任务被名额挡住

**当时**：15:00，`bot#2` 只写方案文档，几乎不占内存，却在排队。原因是 `tasks.max_running` 是 2，名额被 `app#10`（编译发版）和 `app#11`（官网验收）占满。上限定成 2，是因为上午一个编译任务内存峰值到了 13G，被系统杀了两次。

**新架构下**（数字是举例）：

1. 派 `bot#2` 时，资源行是：可用 11.8G；`app#10` 现在 9.1G，历史峰值 13G；`app#11` 0.7G。`bot#2` 的估计 0.6G（同角色写文档的历史峰值）。
2. 预计可用 = 11.8 − (13 − 9.1) − 0.6 = 7.3G，高于底线 1.5G，服务直接开工，不叫醒任何智能体。
3. 假如派的是第二个编译任务（估计 8G）：预计可用 = 11.8 − 3.9 − 8 = −0.1G，低于底线，服务不开。排队超过 15 分钟，给派活方发调度消息，它可以选接着等、改去云端，或者等 `app#10` 编完。
4. `app#10` 的内存真涨到可用不到 0.75G 时，服务冻结优先级最低的单元并上报，保住 bridge。
5. `app#10` 的 `MemoryHigh`、`MemoryMax` 按它的估计设，不再是统一的 6G。

**用到**：第 5 节。
