# 长任务

> 版本 3.8.2 · 2026-11-24 · 维护：Yonty Bot

活儿比较大时（预计十几分钟以上、要改不少代码），聊天里的 Claude 不在当前会话里直接干，而是派成后台任务：在独立的工作树和分支上跑，开工、进展、提问、结果都发回派活的那个会话。体验参考了 OpenClaw、Devin、Cursor 后台代理和 Claude Code in Slack：派活前先给一句计划，过程中只在关键节点说话，有问题就在原会话里问，做完给分支和草稿合并请求。

## 1. 流程

1. 聊天里先把事聊清楚：目标、范围、仓库、验收标准。
2. Claude 在回复末尾写 `[派活]` 块（守则“长任务”一节规定格式）。bridge 拆出这个块，检查仓库，建任务。模型和思考档由服务定（`pick_model`），本机跑、有验证命令的开发活（含没写角色的）先用 sonnet/high（`decide.points.task: on` 时由 jev 打分改成 opus/high 或 sonnet/medium），会话写了也不听，除非主人的话派的、写了 `模型: opus（主人指定）`。没有验证命令或在云端跑的没有自动换人的机会，和别的角色一样：写了听写的，没写用角色模板的默认。项目经理派开发活没写 `验证` 会退回（可以写 无）。同一个会话里不换模型，免得缓存白写。sonnet 验证两次没过（或返工后按失败交回），服务自动换 opus：同一个工作树和分支，新会话，首条提示带上换人原因、最近的验证输出和要重新取的指令；只换一次。审批快照、开工消息和 `/task 短名#N` 都写明用的哪个。任务里派子代理也按子活儿挑模型。实测（2026-11-21）：haiku、sonnet、opus 在 `--permission-mode auto` 下都能正常跑命令，`--effort` 五档都接受。
3. 审批：
   - 主人派的：直接排队。
   - 同事在群里派的：bridge 在**同一个群**里 @ 主人，附任务书快照。主人在群里 @机器人 回 `/approve 短名#N` 或 `/reject 短名#N`。
   - 同事私聊派的：bridge **私聊主人**（优先同一渠道）。主人私聊回 `/approve 短名#N`，bridge 回原会话告诉同事。
   - 只认主人的发送人 ID。24 小时没人批自动作废（`tasks.approval_hours`）。
4. 开工：按资源放行（2.0 起，取代 `tasks.max_running`）。服务每 5 秒看内存余量和压力：预计可用 = 现在可用 − 在跑任务还会涨的部分 − 新任务的估计。低于底线 max(1.5G, 总内存 10%) 不开；单元总数上限 8。估计取 max(`[派活]` 写的 `资源:`, 同类历史峰值)；没有历史时，开发、排查、验收按 4G，其余 1G。够了就用 `systemd-run --user` 起一个独立单元（macOS 用独立进程组）。每次放行和改投记进 `state/decisions.jsonl`，`/why 短名#N` 看理由。bridge 重启不影响任务。字段见 config.md 的 `tasks.resources`。
5. 运行中：Claude 用待办工具列计划；重要节点单独写一行 `[进展] …`，bridge 转发。飞书 30 分钟没动静会发一次心跳（`tasks.heartbeat_min`），企微不发。
6. 提问：Claude 写 `[提问] …` 并结束这一轮，任务变“等回复”。
7. 完成：提交、推送 `bot/<短名>-<N>-<月日>` 分支，用 `python3 <实例>/tasks.py mr --title … --body-file … --target <目标分支>` 建草稿合并请求。GitHub 走 `gh pr create --draft`；Codeup 走 OpenAPI（按远端地址查数字仓库 ID，`workInProgress: true`）。令牌只在这个进程里读，不打印；只建草稿，不合并；非主人只能从 `bot/` 分支建。目标分支取 `[派活]` 的 `目标分支`，工作树也从它切出；没写就用仓库默认分支。
8. 主控收尾（`tasks.relay`，默认开）：完成、提问、失败、中断不直接发给人，而是以 `[任务回报]` 排进派活的那个会话的队列（和聊天消息同一个队，不会两处同时 `--resume`），按派活人的权限跑一轮。主控能自己办的先办：补建合并请求；替任务回答聊天里定过的事，或让它续跑（回复里单独一行 `[任务指令] 短名#N 内容`，可以多行，见 2.2；转进收件箱并重新排队）；然后对人只汇报结果和真正要人定的事。每个任务自动追加和再派活合计最多 3 次。主控没跑成就原话照发；主控回过但没发出去，只重发它的话，不再跑一轮。进展仍然直发。派活人或主人也随时可以回 `@机器人 短名#N 意见`。
   - 2.0 起，bridge 派的任务把任务回报交给所属项目、派活人那个受众的项目经理会话（`proj:<短名>:<会话键>`）。它先收尾，再二选一：`[投递 主控 完成]`（或 `问题`）上交，或者单独一行 `[处理掉] 理由`。两样都没写，服务替它投一条只有结论行和链接的完成（提问就投问题）给主控，记“替项目经理投递”（防沉默，补投的不去重）。项目经理用 `[任务指令]` 答了提问算处理过。项目经理的其余文字只进决策日志，不发给人。主控收到后在派活的聊天会话里跑一轮，回复发回派活的聊天。项目经理没跑成，回报退回主控老路。1.3.0 建的任务照旧回报给原聊天。
   - 投递轮回复里的 `[任务指令]`、`[派活]` 按任务回报的规矩转：只能管派活人能管的任务，每个任务自动追加最多 3 次；这一轮已经是第 3 跳就不转（“超跳不转”）。
   - 内存紧时冻结（方案 5.4）：可用内存低于 `freeze_gb`（0.75G）或内存压力超过 `freeze_pressure_pct`（60%），冻结一个优先级最低的单元：先定时运行，再最晚开的任务。冻了一个之后至少等 `freeze_settle_s`（90 秒，压力是 60 秒均值）再看，可用内存在好转就不再冻，没缓过来才冻下一个。用 `systemctl --user freeze`（实测可用，冻着的单元 `stop` 0.01 秒就停），没有 systemd 单元的用 SIGSTOP 整个进程组。可用内存回到冻结线以上 `thaw_margin_gb`（0.5G，回差）、压力回到 `thaw_pressure_pct`（40%）以下，而且冻满 `thaw_after_s`，按后冻先解解冻。冻满 `freeze_max_min`（20 分钟）还没缓过来，停掉单元、按中断交回，会话和工作树留着。冻结和解冻都记理由、私聊主人；冻着的不算卡住、心跳说“冻着”，有单元冻着时不开新单元。

## 2. 命令

| 命令 | 谁能用 | 作用 |
|---|---|---|
| `/tasks` | 所有人 | 按项目分组列出。主人看全部，别人看本会话的 |
| `/task 短名#N` | 能看到的人 | 状态、计划、最近进展（主人另看花费） |
| `/task brief 短名#N` | 能看到的人 | 完整任务书（审批消息里超过 3000 字的部分截掉了） |
| `/task cancel 短名#N` | 主人、派活人 | 停掉，分支留着 |
| `/task clean 短名#N` | 主人 | 删工作树，分支留着 |
| `/approve 短名#N` / `/reject 短名#N` | 主人 | 审批 |
| `/bind 短名` / `/unbind` | 主人 | 把这个群绑到项目 / 解绑 |
| `/why 短名#N` | 主人 | 看放行或改投的理由（`state/decisions.jsonl`） |
| `/schedules` | 主人 | 定时任务，见 [schedules.md](schedules.md) |
| `/approve 短名#N.aK` | 主人 | 批准授权类动作（`tasks.py act` 提出的第 K 个） |
| `/team` | 主人 | 角色模板和各项目的事 |
| `/stop [短名]`、`/resume [短名]` | 主人 | 停工：在跑的停在原地，排队的不开；复工接着干。不写短名就是全部。主人私聊里单发“停”“先停”等于 `/stop` |
| `/status [短名#N]` | 主人（私聊） | 额度快照、在跑的任务或单个任务为什么停、最近的报错。主控在主人私聊的回复里写 `[服务命令] diag [短名#N]` 是同一份（服务执行，结果交回那个会话） |
| `短名#N 内容` | 主人、派活人 | 主人发的服务直接转；别人发的先交给主控，主控写 `[任务指令] 短名#N 内容` 才转，权限跟本人发一样（只能管自己派的）。转进去以后：运行中通过 PostToolUse 钩子塞进当前会话；等回复/完成/失败/中断后：接着跑同一个会话 |

任务侧命令（任务里用 `python3 <实例>/tasks.py …`）：

| 命令 | 作用 |
|---|---|
| `tasks.py inbox iN` | 取追加指令，取出即回执：`[收到 iN]` 或 `[存疑 iN] 理由`。有没取的指令时不收完成，最多续跑 2 次 |
| `tasks.py send --to 目标 --kind 类别 --text …` | 投递。目标：主人、派活人、聊天、主控、项目经理 短名、短名#N、事 项目/事名、记录。类别：授权、花钱、方向、动作、进展、节点、完成、问题、留言 |
| `tasks.py res` | 看资源余量和估计 |
| `tasks.py act` | 提出动作（修补、授权、花钱、方向、禁止），见 boundary.md |

投递规则：发给主人的只收授权、花钱、方向，其余改投；每个任务、每个会话同一时间只有一条请求挂在主人那里，其余排队，没答的不挡别的任务和会话；不要回复的消息 30 分钟内去重；正文发给主人、聊天、主控最多 300 字，其余 2000 字，截了会在回执里写明；人的答复不截。主人以外的人派的任务发给主人的，送到主人自己的私聊，全文（最多 5000 字）；派活人的会话只收到一句“已转给主人”。

群里要 @ 机器人才收得到，bridge 先去掉开头的 @ 再匹配命令。

### 2.1 任务编号

- 一个仓库（`[派活]` 的 `仓库`）是一个项目。短名默认取仓库目录名的小写，例如 `yonty-bot`、`web-app`；`tasks.project_alias` 可以给某个仓库路径另起短名（见 config.md）。两个不同的仓库目录名一样时，后来的那个加 `-2`、`-3`。
- 每个项目的任务各自从 1 编。开工、进展、提问、完成、心跳、审批、`/tasks` 列表、`/team`、任务回报头和给主控的材料，一律显示 `短名#N`。分支是 `bot/<短名>-<N>-<月日>`。
- 短名和编号在建任务时定下，写进 `task.json` 的 `project`、`num`，之后不变。之后加或改别名只影响新任务：新短名从 1 重新编。
- 所有命令都认 `短名#N`。只写 `#N`（或 `/task N`、`/approve N`）时：
  1. 在能看到的任务里找新编号是 N 的，加上升级前旧号是 N 的（见 2.3）。
  2. 不止一个时，先只留进行中、待批和 7 天内动过的。
  3. 剩一个就用它；剩好几个就回一句，列出候选，什么都不做，让对方带上项目名。`/approve N` 有歧义时，候选里只有一个在等批就批它。
- 内部 id（目录名 `state/tasks/<id>/`、单元名、钩子的 `FCB_TASK_ID`）照旧是全局递增的整数，不给人看。

### 2.2 多行 `[任务指令]`

主控回复里的 `[任务指令] 短名#N 内容`，从这一行起，取到下一个 `[任务指令]`、`[派活]`、`[不回]`、`[/任务指令]` 或回复结束，整段原样转给任务，含缩进和空行。编号后面可以带冒号，内容可以从下一行开始。同一条回复里几条指令各自拆开。

- 给人看的话写在指令前面。非要写在后面，先单独一行写 `[/任务指令]` 收尾，后面的话留在回复里。没有收尾标记时，指令后面的所有行都算指令。
- `[派活]` 起到回复结束都是派活块，里面的 `[任务指令]` 行不拆。聊天里先拆指令再建任务，派活后接的说明不会被吞进指令。
- `[不回]` 结束指令，自己留在回复里。

### 2.3 升级迁移（1.0.0 → 1.1.0）

1.0.0 及以前任务号全局递增。升级后 bridge 第一次启动时，`tasks.migrate()` 给还没有 `num` 的旧任务编号：按项目分组，按创建时间排，接着这个项目已有的最大号往下编。旧全局号记进 `legacy`。

- 只加 `project`、`num`、`legacy` 三个字段，不改 `updated`。分支名、工作树路径、事件、收件箱都不动，旧任务的分支还是 `bot/<旧号>-<月日>`。
- 幂等：编过号的跳过，重启多少次结果都一样。新实例没有旧状态，什么都不做。
- 过渡期旧写法还能用：只写 `#5` 时，旧全局号 5 也算候选。跟某个新编号撞了（旧 `#3` 和新的 `a#3` 不是同一个任务），按歧义处理，两个都列出来。7 天后旧任务多半不在“最近”里，撞号自然变少。
- 迁移在 `state/tasks/.lock` 下做，跟建任务用同一把锁；每个任务的写入走它自己的锁，后台单元正在跑也不冲突。

## 方案和小任务（3.0）

项目经理先写 `[方案] 名称`，里面一行“任务:”，下面一行一个 `- 标题 | 文件 | 依赖`，以 `[/方案]` 收尾，存在 `state/team3.json`。再照单派活，一条回复能写多个 `[派活]…[/派活]`，比普通派活多写：

| 字段 | 说明 |
|---|---|
| `方案` | 登记过的方案名，必写 |
| `标题` | 跟任务单一字不差 |
| `文件` | 独占的文件或目录；跟同项目在跑的小任务撞了就等 |
| `依赖` | 任务单里的标题或短名#N；都完成了才开工，开工先合它们的分支 |
| `再审: 主人同意` | 同一方案的评审默认最多两轮（`team.max_reviews`），第三轮起要主人同意才写，没写退回。取消、失败、中断的不算轮次 |
| `收口: 是` | 最后一个任务，合分支、全量测试、建合并请求 |

没写 `资源` 的小任务开工估算按 2G，只跟同类小任务比历史，不被整仓编译的峰值拖成一个一个跑。小任务的开工、进展不发消息，看 `/tasks`。

## 3. 权限

权限在建任务时按**派活人**定下来，之后不随补充指令的人变化。

| 层 | 主人派的 | 同事派的（主人批过） |
|---|---|---|
| 钩子环境 | `FCB_OWNER=1` | `FCB_OWNER=0`，私密路径照拦 |
| `git_guard.py` | 不能绕过 git 钩子；不能强推或删 main/master | 不能强推、删分支、推标签；gh 只能建草稿合并请求、看 PR/issue/CI、提 issue 和评论、只读 api |
| `hooks/git/pre-push` | 不限 | 只放行 `refs/heads/bot/*`（ref 层面拦，不靠命令字符串） |
| 代码平台凭据 | 不能直接读（`credential_paths`、凭据助手、带令牌的请求头都拦），建合并请求只走 `tasks.py mr` | 同左；`tasks.py mr` 只认 `bot/` 分支 |
| 规则（所有任务） | 不合并、不推主干、不发版 | 同左 |

`pre-push` 通过环境变量 `GIT_CONFIG_COUNT/KEY_0/VALUE_0` 把 `core.hooksPath` 指到实例的 `hooks/git/`，不改仓库配置；分发器做完检查后转给仓库原来的钩子。已实测 Claude Code 的 Bash 工具保留这组变量（它只追加 `KEY_1=credential.guiPrompt`）。

> **警告**：这几层挡得住正常操作和直接的绕法（`--no-verify`、改 hooksPath、`env -i`、`unset GIT_CONFIG_*`、写明推到非 `bot/` 分支），挡不住所有绕法：例如先用 Write 写一个脚本，脚本里清掉环境再推送或调 `gh pr merge`。真正的兜底是 GitHub 上的分支保护：主干开“必须经合并请求”“禁止强推”，机器人用的 GitHub 账号不给绕过保护的权限。

### 3.1 结束和排队（评审修复 12、9，2026-11-23）

- 只读角色（禁用工具含 `Edit`，如评审、产品、需求）不跑验证闸门：它们不改代码，验证命令只会在基线上跑。
- 交回内容写了“按失败交回”，或有一行“结论：…”，按它结束：结论带 BLOCKED、失败、没过之类算失败，其余算完成（完成照样过验证闸门）。只有没写结论的 `[提问]` 才停在等回复。
- 等回复的任务最多挡同一件事的排队 `tasks.wait_block_min` 分钟，过了让排队的先跑，并给主控发一次提醒。
- 跑验证命令期间来了新指令，不收“完成”，带编号续跑。
- 发给主控、项目经理的投递先记成 `handing`，会话那一轮处理完才标已送；服务中途重启，下一拍重新送，最多 3 次。

## 4. 存储

- `<实例>/state/tasks/<id>/`（内部 id，不是 `短名#N`）：`task.json` 状态（含 `project`、`num`，迁移来的还有 `legacy`），`events.jsonl` 要发回聊天的事件，`inbox.jsonl` 补充指令（`inbox.off` 记已交出的条数），`stream.log` Claude 原始输出。
- 工作树：`<tasks.root>/<服务名>/<id>`，默认 `~/work/.bot-tasks/`。从远端默认分支最新代码切出。定时运行的是独立的 `git clone --shared`，每轮结束把 `bot/` 分支拉回主仓库，原因见 boundary.md“定时运行的沙箱”。
- bridge 记已发到第几条事件（`posted`），发完再记，重启后不丢不重。飞书每条用不同的幂等键。
- 单元没了但状态还是“进行中”：标成“中断”并通知，不自动重跑；回 `短名#N 继续` 接着干。

## 5. 订阅额度

任务用的是机器的 Claude 登录态（`claude -p` 计入订阅额度，见官方 “Use the Claude Agent SDK with your Claude plan”）。检查点和额度提醒见第 6 节；`/task 短名#N` 给主人看已用、检查点和订阅额度。本机同时跑几个由资源放行定（第 1 节第 4 步），云端任务不占本机资源。

## 6. 团队与资源（3.0）

两个来源：Lauren Tan（土豆姐，pstack 作者）的“倒金字塔”——能让程序判定的规矩写进代码，守则这类文字只管要判断力的事；主人要的团队结构——一个协调人，配产品、需求等专家和一组开发，每个项目从同一套模板派生自己的兄弟智能体，各自保持上下文。pstack 移植版（michael-denyer/pstack-claude）里的做法是“按角色定模型、默认新开子代理”，团队结构是在它上面按主人的要求加的，只查过这个移植版。

### 6.1 角色

| 角色 | 是谁 | 做什么 | 靠什么保证 |
|---|---|---|---|
| 协调人 | 聊天里的主控会话 | 聊清需求、拆活、按角色派、收回报、把关、对人汇报 | `chat_max_turns`：一轮步数到顶就把剩下的写成 `[派活]` |
| 产品 / 需求 | 角色模板 | 只出方案文档、任务单和验收清单 | `禁用工具: Edit NotebookEdit`，改不了已有文件 |
| 开发 / 排查 / 杂活 | 角色模板 | 写代码、找根因、机械活 | 默认模型分别是 sonnet / opus / haiku |
| 评审 | 角色模板 | 合并前只读看改动 | `禁用工具: Edit Write NotebookEdit`，`续接: 否`（每次新开，不带以前的印象） |
| 验收 | 角色模板，服务派 | `验收: 独立` 时，负责人开工前只看任务书写验收测试并提交 | 负责人改了这些文件，验证闸门退回；见 6.1.1 |
| 验证 | 服务本身 | 复跑 `[派活]` 的 `验证` 命令 | 不过就退回同一会话返工，最多 `verify_retries` 次 |
| 主人 | 人 | 合并、上线、产品方向 | 任务只建草稿合并请求 |

角色模板放在实例的 `roles/*.md`，`scaffold.py` 缺哪个补哪个，已有的不覆盖。文件头写 `名称`、`模型`、`思考`、`续接`、`适合`、`禁用工具`、`不带顾问`，正文是给该角色的工作要求，开工时拼进任务的首条提示。`禁用工具` 以 `--disallowedTools` 传给 CLI。`不带顾问` 写模型名，用这些模型跑时设 `CLAUDE_CODE_DISABLE_ADVISOR_TOOL=1`，不带顾问（advisor）工具；开发默认 `sonnet`，换 opus 后带上。主人发 `/团队` 看模板和兄弟智能体。

#### 6.1.1 独立验收

`[派活]` 写 `验收: 独立`（只认这两个字）时，任务分两段跑，都在同一个工作树、同一个分支上：

1. 服务记下当前提交（`accept_from`，只记一次），用 `roles/验收.md` 开一个新会话（不分叉、不当负责人的会话头）。它只看任务书和现有代码，写测试并提交；没提交的服务替它提交。单段上限是任务检查点的 30%，花费记进任务（`accept_cost`）。
2. 这次提交新增的文件记成 `accept_files`，只锁这些；它改了已有文件的，告诉负责人，不锁。最后一条回复里的 `[验收命令]` 记成 `accept_cmd`，派活没写 `验证` 时也拿它当验证命令。
3. 有验收命令就当场跑一次：功能还没写就通过，说明测试没测到东西，结论行写出来。
4. 验收做完才判断能不能分叉负责人的会话（验收跑得久，缓存可能已经凉了）。负责人的首条提示里列出锁住的文件，说明不许改。负责人那段没起来、重跑时，不重做验收，说明照样带上。
5. 验证闸门：先看 `git diff <验收提交> -- <锁住的文件>`（含没提交的改动），有改动就按验证不过退回；再跑 `验证`；验收命令和它不同时再单独跑一遍。没有验证命令时闸门不拦，结论行写出改了哪些。
6. 测试确实写错了：负责人用 `[提问]` 说明，主人或主控回 `放开验收测试` 后不再查、不再单独跑。同事写的不算。
7. 不做独立验收的情况：实例里没有 `roles/验收.md`、任务角色是只读的（评审）、验收没写出新文件或异常退出（分支退回 `accept_from`）。照常开工，结论行写“没有独立验收”。云端任务不做独立验收，改在本机跑。

依据：AgentCoder（2023，作者自测，GPT-3.5，HumanEval）里只有写代码的智能体 61.0%，加上独立写的测试 64.0%，再加上跑测试、把结果反馈回去 79.9%。提升主要来自“独立测试 + 跑测试反馈”一起用，这正是验收加验证闸门的组合。MAST（2025）里验证缺失或出错约占多智能体失败的四分之一。按角色接力写代码，没找到同一底座模型下胜过单个负责人的可靠对照。

只用假 CLI 测过，还没在真实任务上跑过。

### 6.2 事和负责人

一件事是项目里一块需要长期有人管的东西。负责人的键是“项目 × 事”，不分群聊私聊、不分派活人，状态在 `state/team/<项目>/<事>.json`，笔记在同名 `.md`，项目约定在 `_约定.md`。带 `audience` 字段的旧文件（按聊天分负责人时留下的）不再读。`[派活]` 的 `事情` 不写就归到主线。

- **负责人是“事 + 档案”，会话可以换**：缓存还热（`sibling_warm_min` 分钟内用过、上下文不超过 `sibling_max_ctx`、模型相同）就用 `--resume <上次会话> --fork-session` 接着干；否则新开会话，提示里带上档案。缓存过期后续接一个大会话要把整段上下文重写进缓存，比读一份档案贵得多。
- **档案只有服务写**：任务最后的 `[交接]` 段按栏解析。`现状`、`待办` 整栏替换；`决定` 追加、去重，最多留 40 条；`约定` 记到项目级，同项目所有事都看得到；`通知 某事：` 记到那件事的“别处留言”，只给已有的事，否则留在笔记里；其余进笔记。档案太长时先丢笔记，目标、现状、待办、决定留着。
- **同一件事同时只跑一个任务**：`thing_busy` 看到同一个键有任务在跑或停在提问，后来的留在“排队中”。失败、中断的不挡。不同的事可以并行。
- **会话头按模型分**：缓存按模型分，换模型的活记在自己那个模型下，不挤掉原来的。会话头所属的任务停在提问、失败或中断时，不拿来分叉。
- **名字相近的归到已有的事**：派活写的名字和已有的一样，或一个包含另一个且只有一件对得上，就归到已有的。新开的事，派活回复里会列出已有的。
- **帮手不顶替负责人**：`续接: 否` 的角色（评审）每次新开，只往档案和笔记里写，不改负责人的会话头。
- **跨事的改动**：交给一个负责人一次改完，用 `通知` 告诉受影响的事。不分给几个负责人同时写。
- **权限按派活人身份分**（`by_owner`，来自 IM 层识别）：会话照样分叉、照样当会话头，话由主控把关；同事派的任务交回的 `决定` 带 `guest` 标记，档案里写明“没确认”；`约定` 记进笔记，不进 `_约定.md`。派活回复和任务回报只在主人私聊里列项目现有的事。审批消息写明归到哪件事。

### 6.3 资源：检查点和额度提醒（都不花 token）

1. **任务检查点**：`[派活]` 的 `预算` 由主控估，括号里写依据；没写就按同类任务历史估（同角色同模型最近 10 个完成任务花费中位数 × `budget_factor`，不够 2 个就只看同模型，再没有用 `budget_default`）。单位是美元当量：CLI 按 API 标价算出的 `total_cost_usd`，订阅不实付，只用来比较任务大小，因为它是唯一能按任务分开算的数。每轮传 `--max-budget-usd 剩余`，到了任务停下、按“到检查点”交回主控，主控写 `[任务指令] 短名#N 继续，预算加到 X` 就接着跑，不用问人。实测：`total_cost_usd` 是会话累计值，`--resume` 后接着累计，记账取增量。
2. **订阅额度提醒**：任务的 `stream-json` 输出里有 `rate_limit_event`，带 5 小时和 7 天两个窗口的用量（整个订阅，含终端里的会话）。服务存到 `state/tasks/quota.json`，每 5 分钟看一次：5 小时窗口过 `quota_alert.five_hour`，或 7 天窗口“已用比例 ÷ 已过时间比例”过 `quota_alert.seven_day_pace`，就私聊主人一条，同一窗口每涨一成只提醒一次。只提醒，不停任何活。2.0 的“每日预算”已删掉。
3. **卡死检测**：本机任务 `stuck_min` 分钟内没调工具、没输出，且进程 CPU 平均不到 5%，先叫项目经理，15 分钟没处置叫主控，120 分钟没人管才停。长时间编译、跑测试时 CPU 在涨，不算卡住。
   验证命令超过 `verify_timeout_min`、别的智能体一轮超过 `max_min` 也是这样叫。上级用标记处置（单独一行，服务直接执行，代码块和派活块里的不算）：
   - `[处置] 短名#N 继续等 30|重跑|按失败收 理由`
   - `[改验证] 短名#N 命令`，下一行 `理由：…`；`[取消任务] 短名#N 原因`；`[改依赖] 短名#N 标题|无`
   验证在 `gate.py` 里跑：完整输出在 `<tasks.root>/gates/<id>/gate-<n>.log`；重测试（上次跑过 3 分钟以上，或没跑过但像全量测试）排队取 `state/heavy.lock`，终端里跑全量用 `flock <实例>/state/heavy.lock 命令`。没跑完的不返工、不换模型。
   依赖的任务失败、取消，或等答复 15 分钟没人回，服务催项目经理；等答复 30 分钟告诉派活人。
4. **结论行**：完成回报第一行是 `PASS`（服务复跑验证通过）或“没定验证命令”；失败写 `BLOCKED` 和原因；到检查点写“到检查点”。

### 6.4 云端执行

`[派活]` 写 `执行: 云端`，活儿在 Claude 官方云端的一次性例程里跑，不占这台机器的 CPU 和内存（不省订阅额度）。

- 条件（`tasks.cloud_ok`）：配了 `tasks.cloud.environment_id`；派活人是主人本人；仓库远端是 GitHub。不满足就改在本机跑。云端没有本机的钩子，公司 Codeup 仓库不上云。
- 开工：起一个一次性的 haiku 会话，只开 `Read` 和 `RemoteTrigger`，建例程并立即运行（约 0.007 美元）。同一任务上一个例程没交结果时不重开。
- 等结果：bridge 每 2 分钟 `git ls-remote` 看分支头，看到 `Cloud-Run: done` 就把分支拉回任务工作树复跑验证命令，过了建草稿合并请求、结论 PASS，没过按 BLOCKED 交回；`Cloud-Run: stopped` 算提问。超过 `cloud.timeout_min` 算中断。
- 续做要新开例程，从分支头接着干；云端没有负责人的会话续接，但开工时同样读档案。

### 6.x 3.1 的修正

- 花费：`--fork-session` 出的会话，`total_cost_usd` 带着父会话的累计。分叉时把父会话的累计记成 `cost_base`，任务花费 = 会话累计 − `cost_base`。
- 项目名是仓库目录名加真实路径哈希，同名仓库不撞。（3.2.1 按聊天分负责人，1.0.0 起改成只按事分，见 6.2。）
- 角色检查：禁了 Edit 的角色干完后看 `base...HEAD` 和未提交改动。评审有任何改动、产品和需求改了已有文件，回报末尾写明。Bash 仍能写文件，所以这是事后检查，不是拦截。
- 预算：主人和主控能写“预算加到 X”；同事写的不算。不在检查点、剩余不到 max(5, 预算×25%) 时来新要求，自动续到 已用 + max(5, 预算×50%)。

### 6.y 缓存过期前压缩（3.2）

- 实测依据（2026-11-21）：
  - 聊天日志 86 轮里，空闲超过 1 小时后的缓存重写占全部缓存写入约三分之一；其中多数空闲超过私聊 6 小时换新时间，压缩也用不上。
  - 本机历次自动压缩：压缩前约 21–28 万 token，压缩后摘要 0.6–3.6 万。
  - 压缩本身要读一遍上下文、写一份摘要，缓存也要重写，小会话压了反而更贵。
- 规则：上下文到 `min_ctx`（默认按价格算，约 8.9 万）、闲置 `idle_min`（默认 50 分钟）到 60 分钟之间，压一次。
  - 任务：只压等人回话的（`waiting`、`failed`）。压缩中来了回复，等压完再开工。压缩的钱记进总账，加到 `cost_base`，不算任务花费。
  - 聊天：私聊等闲置换新时间超过 1 小时的会话才压，排进会话自己的队列，不和消息同时续接。旁听会话不压。
- 无头调用 `claude -p --resume <id> --output-format json`，输入 `/compact 保留：…`。结果的 `result` 是空的，`total_cost_usd` 是会话累计，含压缩这一次。

### 6.5 没做的（判断）

- 同题多跑择优、跨模型交叉评审的自动扇出：花费是单线程的 3–10 倍。需要时主控派一个“评审”角色任务。

## 智能体适配层

任务用哪个智能体 CLI 跑，由 `agents.py` 的适配类决定，每个任务开工时选定（`agent` 字段），续跑、返工都用同一个，缓存不断。

| | Claude Code | ZCode（GLM） |
|---|---|---|
| 沙箱 | 定时运行才进 | 一定进：看不到 Claude 登录态、凭据、私密目录，只能写工作树 |
| 护栏 | `claude-settings.json` | 同一套钩子，由 `hooks/agent_hook.py` 转跑；钩子出任何错都按拦下 |
| 分叉、压缩、按花费截停、终端接手 | 有 | 没有；按时间和请求次数截停 |
| 推送和合并请求 | 任务自己做 | 验证过了由服务做 |

- 选：`[派活]` 写 `智能体: ZCode` 或 `Claude`；不写时，配了试点的仓库里，主人派的、本机跑、有验证命令、非前端、风险低的开发活先给 ZCode。没配 `tasks.agents.zcode` 就全是 Claude。
- 换：验证没过、按失败交回、拥堵跑不完、钩子没触发、模型不对、超时，都换 Claude。前一个写压缩摘要（写不出由服务按 git 记录补），没提交的改动存成一个 `wip` 提交，工作树换回主仓库的正常工作树，Claude 开新会话。
- 试点：`/status` 里看派了几个、一次过几个、用量。先试 `trial` 个，一次通过率低于 `min_pass` 自动停。取消的和没跑成的（拥堵、沙箱、护栏没触发）不算成绩；没跑成满 5 个也停。
- 加一个智能体：在 `agents.py` 加一个类（命令、环境、沙箱挂载、事件翻译、能力），登记进 `AGENTS`。

## 小任务变更同步到私聊

主人私聊派的方案，小任务的开工、进展、完成、失败、等答复、停了，由服务直接发到那个私聊（20 秒内的合成一条），不走模型，也不进主控的前文。群里和同事那边不发。

## 飞书任务同步

`feishu_tasks.enabled` 打开后，`feishu_tasks.py` 把主人私聊派的活同步成飞书任务：一个方案一条，不在方案里的一个任务一条，机器人负责、主人关注。状态、步骤、`[进展]`、结论都由服务照任务状态写，不走模型；做完服务勾掉。主人在飞书任务里指派给机器人，等于私聊派活；只接主人建的、没有别人参与、不在清单里（机器人看得到的）的任务，评论只认主人的。每条任务往来源私聊发一行带标题的任务链接（会进会话侧栏的“任务”；卡片、会话成员都进不去，2026-11-24 实测），只发一次，进度看侧栏里的任务。在飞书自动给智能体建的清单“智能体负责的”里，一个项目一个分组；要机器人身份的 `task:tasklist:write`，没有就只是不分组。主人勾掉的不再重建；勾掉不等于取消，要停写 `/task cancel`。
