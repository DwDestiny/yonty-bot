# 搭建指南（给帮你安装的智能体看）

> 3.21.0 · 2026-11-28 · 维护：Yonty Bot contributors

## 它是什么

一个常驻进程（`bridge.py`）每个渠道开一个接收线程：飞书用 `lark-cli event consume`，企业微信用子进程 `wecom_gateway.mjs`（官方 SDK 长连接）。两边的消息归一成同一种事件，每个会话交给一个无头 `claude -p` 会话处理，结果按原渠道回去。企微细节见 [wecom.md](wecom.md)。

| 部件 | 作用 |
|---|---|
| `bridge.py` | 收消息、过滤（群里只收 @ 机器人的）、带前文、调 Claude、回复 |
| `rules.md` | 守则：人设 + 表达风格 + 边界，每次会话用 `--append-system-prompt-file` 加进系统提示 |
| `hooks/lark_identity.py` | 硬限制：按发消息的人，限制 lark-cli 能用哪个身份 |
| `hooks/private_guard.py` | 硬限制：主人私聊以外，挡私密路径；知识库全库搜索自动跳过私密目录 |
| `hooks/wecom_guard.py` | 硬限制：wecom-cli 带主人的企微授权，按发消息的人限制能调什么（不论是否启用企微都挂） |
| `wecom_gateway.mjs` | 启用企微时生成：收企微消息、回“思考中”再更新成结果、下载附件 |
| `tasks.py` + `hooks/task_inbox.py` | 长任务：派活、审批、后台运行、进度回报，见 [tasks.md](tasks.md) |
| `hooks/mcp_guard.py` | 硬限制：MCP 工具只给主人本人触发的会话用（`mcp_open_to` 里的除外） |
| `hooks/command_guard.py` | 硬限制：按 `command_guard` 规则限制哪些会话能跑某类 Bash 命令（例如 `mcporter`） |
| `upgrade.py` | 主人发 `/upgrade` 后由服务起的独立升级单元：快进、跑测试、备份、装新版本、重启，起不来就回滚（不等任务，见 3.1.0） |
| `hooks/git_guard.py` + `hooks/git/` | 硬限制：git/gh 能做什么；推送前查密钥；非主人触发的推送只能推 `bot/` 分支 |
| `claude-settings.json` | 权限拒绝表 + 挂钩子（脚本生成） |
| `config.json` | 实例的全部可调项 |

会话划分（企微同样，key 加 `wx:` 前缀，与飞书互不串）：私聊一个人一个会话（闲置 6 小时或发 `/new` 开新的）；群里直接发的消息整个群一个会话（闲置 2 小时开新的），话题里的消息一个话题一个会话；开了旁听的群另有一个旁听会话。

**回复方式**：默认引用原消息直接回在群里或私聊里，不开话题；原消息在话题里才回在话题里。要单独提醒某人时，Claude 用 `<at user_id="open_id">名字</at>` @ 出来，前文和消息头都带 open_id；bridge 会把 @所有人 换成普通文字。

**长任务**：大活儿不在聊天里干。Claude 用 `tasks.py do` 交一个 `[派活]` 块，主人派的直接开工；同事派的先找主人批（群里就在群里 @ 主人，私聊就私聊主人）。任务在独立工作树和 `bot/` 分支上后台跑，开工、进展、提问、结果都回到原会话，做完推分支、建草稿合并请求。模型和思考档由主控在 `[派活]` 里按活儿挑，便宜的活用 haiku、sonnet。任务号按项目分开编，写成 `短名#N`。命令 `/tasks`、`/task 短名#N`、`/approve 短名#N`、`短名#N 内容`，`/help` 列出全部。见 [tasks.md](tasks.md)。

**旁听**：默认所有群只收 @ 机器人的消息。主人在某个群里发 `@机器人 /listen on`，这个群就进白名单：没 @ 的消息也读，每 40 秒拉一次，群里安静 25 秒后整批交给 Claude，由它决定接不接话（接梗、吐槽、提到主人或机器人时），默认不出声，插话后冷却 10 分钟。`/listen off` 关闭，`/listen status` 查看。权限见 [boundary.md](boundary.md) 第 4 节。

## 开工前问清六件事

以下六件决定实例怎么生成。用户没说的，用 `AskUserQuestion` 一次问完，每题给推荐项。

1. **跑在哪**：服务器（推荐，常驻不掉线）还是本机电脑（合上盖子就收不到消息）。细节见 [setup.md](setup.md) 第 1 节。
   > **警告**：机器人用的是这台机器上 Claude Code 的登录态和额度。先确认用户允许在这台机器上长期跑带登录态的 Claude。用户有“登录态只在某些机器触发”这类规则时，以用户规则为准。
2. **渠道和应用**：接飞书、企业微信，还是两个都接（`channels`）。
   - 飞书：已经有 lark-cli 应用就复用，没有就新建。复用前要查清它的事件有没有别的程序在收（同一个应用的消息只会推给一个接收方）。见 setup.md 第 2 节。
   - 企微：`wecom-cli auth init` 扫码建智能机器人，同一个机器人只能有一条长连接。见 [wecom.md](wecom.md) 第 2、3 节。
3. **人设**，决定边界：
   - `work` 工作分身：在工作群替主人汇报进度、答疑、对接、记 bug。工作内容大方聊；人物资料、对公司和同事的私下看法、主人私事不外露。
   - `personal` 私人助理：只为主人服务。日程、行踪、健康、家庭、财务一律只对主人说；别人只能聊通用问题。
4. **表达风格**（`style`）：
   - `veteran` 干练老同事：只给结论，语气硬，带点梗（第一个实例用的就是这个）。
   - `tsundere` 傲娇毒舌：同上，套话的人会被怼回去（“本尊可是尊贵的 Claude”）。
   - `warm` 温和专业：先结论后原因，不玩梗，适合对外或新人多的群。
   - `minimal` 极简冷静：一句话，不寒暄，不用 emoji。
5. **边界细节**：哪些目录和知识库分区算私密（填 `private.paths` 和 `private.search_roots`）；同事触发时能不能用主人身份读聊天记录（`identity.others`）。见 [boundary.md](boundary.md)。
6. **跨 IM 读取**（两个渠道都接时才问，`cross_im_read`，默认关）：飞书里的会话能不能读主人的企微聊天记录，企微里的会话能不能读飞书的。
   > **警告**：用户要打开时，先把这几点告诉用户并等用户明确同意：同事触发时也能跨读（`identity.others` 为 `bot_read_im` 时）；读到的内容会不会被转述到另一边，只靠守则和 Claude 把关，钩子不拦；不想让同事触发跨读就把 `identity.others` 设为 `bot`。用户同意后，第一次运行 `scaffold.py` 加 `--confirm-cross-im`（脚本不加这个参数会打印同样的提醒并停下）。

## 步骤

下面所有命令都在**仓库根目录**（克隆下来的 `yonty-bot/`）里执行，路径都从仓库根算起；`<实例目录>` 换成你自己的目录。样例配置里的 `~/work`、`~/wiki`、`~/notes/kb` 是作者习惯的目录，一律换成你自己的。

0. 先备好工具（官方安装途径，命令以官方页面为准）：
   - Node.js：下面三个 npm 包对 Node 版本要求不同（2026-11-25 用 `npm view` 查）：`@larksuite/cli` ≥16，`@wecom/cli` ≥18，`@anthropic-ai/claude-code` 2.1.332 声明 ≥22。三样都要装就直接用 22 或更新的。
   - Claude Code：`npm install -g @anthropic-ai/claude-code`，再运行 `claude` 登录。官方说明见 <https://code.claude.com/docs>。
   - lark-cli：`npm install -g @larksuite/cli`。装完用 `lark-cli --version` 确认。
   - 要用到的可选依赖：`gh`（GitHub 建合并请求）、`bwrap`（`apt install bubblewrap`，带读范围的定时任务要）、systemd 用户服务（Linux 常驻）。Mac 没有 bwrap 和 systemd，看门狗和 `/upgrade` 在 Mac 上用不了；Mac 上任务怎么跑没有实测。
1. 登录 lark-cli：`lark-cli config init`（新建应用加 `--new`），再 `lark-cli auth login`。登录要用户在浏览器点，按 setup.md 第 2 节把链接交给用户。
2. 在飞书开发者后台给应用开机器人能力、加权限、订阅 `im.message.receive_v1`（长连接）、发布版本。清单见 setup.md 第 3 节。
3. 建实例目录并复制样例配置：`mkdir -p <实例目录> && cp app/config.example.json <实例目录>/config.json`，例如 `<实例目录>` 写 `~/work/<机器人名>`。
4. 接飞书时运行 `bash scripts/ids.sh`，把输出的 `bot_open_id` 和 `owner_open_id` 填进 `<实例目录>/config.json`；任何一项取不到，脚本会打“标签 （取不到）”、在 stderr 写原因，并以退出码 1 结束，先看 stderr 再填。接企微时按 wecom.md 第 2 节填 `channels.wecom`。再按问到的六件事填 `persona`、`style`、`private`、`identity`、`workdir`、`add_dirs`。
   > **注意**：`workdir` 不能是实例目录，否则 Claude 会加载实例目录的 `CLAUDE.md`。一般填主人放代码仓的目录。新装前先建好 `workdir` 指向的目录，不存在会停下（装过的实例只警告）。
5. 运行 `python3 scripts/scaffold.py <实例目录>`。脚本先检查再写盘：配置缺项、`workdir` 不存在（新装）、启用企微却没有 npm，都会报错退出，什么都不写；npm 没有时的提示是“启用了企微，但没找到 npm：装好 Node 18+ 再跑；或加 --no-npm 先生成，之后自己装依赖”。通过后写出 `bridge.py`、`hooks/`、`rules.md`、`claude-settings.json` 和服务文件，启用企微时另写 `wecom_gateway.mjs` 并 `npm install` SDK。结尾打印 `完成（Yonty Bot vX）`；如果打的是 `完成（Yonty Bot vX），还差 N 样：`，下面逐条列出的（没装 claude 或 lark-cli、npm 装失败等）都要补齐。
   > **注意**：服务的 PATH 在生成这一刻写死。先装好 claude、lark-cli（装到 `~/.local/bin` 也一样）再跑 scaffold；后装的，装好后重跑 scaffold。看门狗单元同样带这份 PATH，Linux 和 Mac 都适用。
6. 读一遍生成的 `rules.md`，按用户的具体情况改：私密内容的具体名单、要找谁拍板、哪些事不在飞书里做。以后改守则直接改 `rules.md`；重跑 `scaffold.py` 只把模板的改动合进去，不盖掉你的改动（加 `--rules` 才整份重写）。守则是空的（或只有空白）时，重跑会按模板补回；有内容就不重写。
7. 验证缓存：在实例目录运行 `python3 bridge.py --cache-check 3`。结论是“正常”才往下走。出错时打印 `缓存检查没跑完：原因` 并以退出码 1 结束（没装 claude、输出不是 JSON 等），按原因处理后重跑。看不懂或异常，读 [cache.md](cache.md)。
8. 照 scaffold 打印的命令安装服务并启动（命令里已带 `mkdir -p`，不用另建目录；Linux 是 `~/.config/systemd/user`，Mac 是 `~/Library/LaunchAgents`）。服务器上还要 `sudo loginctl enable-linger $USER`（要 sudo，交给用户）。
9. 启用看门狗（Linux）：scaffold 会生成 `<服务名>-yb-watchdog.service` 和 `.timer`，单元里已带 PATH，但不会自动启用。心跳 5 分钟没更新就私聊主人，不靠 bridge 活着。在终端跑：`systemctl --user link <实例目录>/<服务名>-yb-watchdog.service <实例目录>/<服务名>-yb-watchdog.timer && systemctl --user enable --now <服务名>-yb-watchdog.timer`。Mac 不生成这两个文件。
10. 跑下面的验收清单。

> 以上命令在沙箱里分别跑过（假 lark-cli、假 claude），服务安装只验证到建链接。没实测：真实飞书和企微、真实 Claude 登录、真实 systemd 启动、Mac。哪里卡住先看 [troubleshooting.md](troubleshooting.md)。

## 验收清单

每条都要真的发消息试，不靠读代码判断。

| 试什么 | 预期 |
|---|---|
| 主人私聊发“在吗” | 几秒内出现“处理中”表情，随后回复 |
| 拉进群，不 @ 发一条 | 没有任何反应；日志里没有 `recv` |
| 群里 @ 机器人问个问题 | 引用该消息直接回在群里，不开话题 |
| 群里让机器人“提醒某某确认一下” | 回复里 @ 了那个人，对方收到提醒 |
| 同一个群再 @ 一次问“刚才说了啥” | 能接上；日志 `context` 行只补新增消息 |
| 同事身份（或请同事）在群里打听私密内容 | 按人设拒绝，不承认有这回事 |
| 同事让它“以主人名义发消息”或读私密目录 | 钩子拦下，机器人改口或拒绝 |
| 主人在群里发 `@机器人 /listen on`，再让人在群里发一句不 @ 的普通对接和一句吐槽 | 回复“开始旁听”；普通对接不出声，吐槽可能被接一句；日志有 `ambient ... -> silent/reply` |
| 企微私聊机器人一句；企微群里 @ 它一句 | 先出现“思考中”，再变成回复；日志 `recv` 行渠道是 wecom |
| 同事在企微让它读主人企微邮件或文档 | `wecom_guard` 拦下 |
| 跨 IM 读取关闭时，在企微让它翻飞书群记录 | 钩子拦下；打开后能读 |
| 飞书开一个新会话，再企微开一个新会话 | 第二个的 `cache_write` 也在 2000 以内（两个渠道共享缓存） |
| 主人私聊让它做个改代码的大活儿 | 先给计划和 `[派活]` 被换成“排上了，任务 短名#N”；随后收到开工、进展、完成（分支和草稿合并请求） |
| 同事在群里派活 | 群里 @ 主人等批；主人 @机器人 `/approve 短名#N` 后开工；同事 `/approve 短名#N` 被拒 |
| 运行中 @机器人 `短名#N 加个要求` | 回“转给 短名#N 了”，任务按新要求调整 |
| 两个项目都有 1 号任务时 @机器人 `#1 加个要求` | 回一句列出 `a#1`、`b#1` 两个候选，哪个任务都不动 |
| 同事任务里让它推 main 或合并 | `git_guard` 或 `pre-push` 拦下 |
| 任务里提交一个像 AWS 密钥的字符串再推分支（主人派的也一样） | `pre-push` 拦下，说是哪个文件哪一行、值打码 |
| 方案没收口时再登记一个新方案 | 项目经理收到回执，回执点明这个版本的负责人，让它把需求点用 `[任务指令]` 交给负责人 |
| 方案任务单里写两个不带第四栏的任务，或派 `收口: 是` | 项目经理收到回执：一个版本只派一个负责人，不派收口 |
| `/task cancel 短名#N` | 单元停掉，状态“已取消” |
| 派一个带 `验证:` 的活，验证命令第一次必然不过 | 任务被退回返工；完成回报第一行是“结论：PASS” |
| 主人派一个 `事情: 登录` 的活，做完后一小时内再派同一件事的活 | 第二个任务的 `/task 短名#N` 写“接着“登录”负责人上次的会话干”；`/team` 列出这个项目的开发兄弟 |
| 同事派同一件事的活，主人批了以后 | 归到同一件事，接着它的负责人干；同事发的 `短名#N 内容` 由主控回复，主控写了 `[任务指令]` 才转进任务 |
| 主人派活时写 `验收: 独立` | 开工消息之后先有一个验收提交；完成回报的结论行写“独立验收测试 N 个文件，负责人没改” |
| 派活写一个很小的 `预算` | 任务停在检查点，主控收到回报后写 `[任务指令] 短名#N 继续，预算加到 X`，任务接着跑 |
| 主人派一个 GitHub 仓库的活，写 `执行: 云端` | 开工消息写“云端执行”；本机没有新单元在跑；做完收到报告和草稿合并请求 |
| `/task 短名#N`（主人） | 显示花费和上限、验证命令 |
| 聊天里让它用后台命令等一个长命令，先回一句 | 先收到那一句，命令跑完再收到第二条（两条都到） |
| 主人私聊发 `/status`、`/help`；同事发 `/status` | 主人马上收到额度、在跑的任务、最近报错和命令清单；同事被拒 |
| 源码仓库 main 有新提交时，主人私聊发 `/upgrade` | 先回“开始升级”，测试过后回“马上重启”，重启后回“升级好了：旧 → 新”；`state/started.json` 是新版本 |
| `grep cost logs/bridge.log` | 新会话首条 `cache_write` 在 2000 以内（守则刚改过的第一次除外） |

## 运维

- 看日志：`tail -f <实例>/logs/bridge.log`。`recv` 收到、`context` 带了几条前文、`cost` 每次花费和缓存读写。
- 改守则后不用重启，下一个会话生效；第一次会整段重写缓存一次（约 $0.2）。
- 改 `bridge.py` 或 `config.json` 后重启服务。停服务用 SIGTERM（`systemctl --user restart`），不要 `kill -9`。
- 升级：在仓库里 `git pull` 后重跑 `scaffold.py`，会覆盖 `bridge.py` 和钩子，保留 `rules.md` 和 `roles/` 里已有的模板（新角色会补上）。服务沿用原来用的那个 Python（它没了或低于 3.9 才换成现在这个）。守则是软链或只读的，脚本不写，会列出来请你手工合。

## 踩过的坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 服务一启动就退出，stderr 有 `reason: signal` | `event consume` 不限时运行时把 stdin EOF 当退出信号，systemd 默认 stdin 是 /dev/null | 模板已用管道保持 stdin 打开 |
| 每条消息都花 $0.18 左右 | 会话开头的 CLAUDE.md、skill 清单每次重写缓存 | 模板已用“固定开场白 + --resume”，见 cache.md |
| 机器人读群历史报 230027 | 机器人身份读群历史要开“读取群内所有消息”权限，一开每条群消息都会推过来 | 前文用主人的用户身份读（`context.read_as`） |
| 发送人名字显示成 open_id | 机器人没有通讯录权限 | 模板用主人用户身份查名字 |
| 守则写“少说废话”仍然啰嗦、语气软 | 抽象要求不管用 | 守则里放“别这样 / 要这样”的真实对照例子，见各 `style-*.md` |
| 边界写得太宽，工作群里连项目都不让聊 | 把“工作内容”和“私下看法”混在一起拦 | 只拦人物资料、私下评价和私事，见 boundary.md |
| 复用 `--session-id` 报 already in use | 一个 ID 只能新建一次 | 出错时丢掉会话映射，下一条开新会话（模板已处理） |
